- `dominance_check` (7a, hard fail, opt-in) — via `expect_hero=True`.

**One thing I should have used and didn't, by the manual's own checklist:** Workflow C's steps

## The one big finding: `render()`'s "full preflight for free" claim is false for HTML checks

`engine/build.py`'s `render()` docstring says: *"pass `elements` ... and render also runs the
full layout.preflight static gate for free."* CLAUDE.md §7a lists `invisible_craft_scan`,
`wash_scan`, `double_rotation_scan`, `antipattern_scan` as living "in preflight" (some flagged
manual-only, some not). Reading `engine/build.py` line by line (not obvious from either
docstring) shows `render()`'s own internal call is:

```python
layout.preflight(W, H, elements, html=None, color_pairs=color_pairs, page_bg=page_bg, core=core,
                 expect_hero=expect_hero, collision_ignore=collision_ignore, containers=containers,
                 text_pairs=text_pairs, cascade_stacks=cascade_stacks, reading_order=reading_order,
                 contains=contains, occlusion=occlusion, auto_nudge=auto_nudge)
```

`html=None`, always — no parameter on `render()` lets a caller change that. Every check inside
`preflight` that is gated on `if html is not None:` (`invisible_craft_scan`, `wash_scan`,
`double_rotation_scan`, plus `preflight`'s own `css_var_check`/`img_src_check` calls, which are
redundant with but distinct from `render()`'s separate top-level `css_var_check` call) **never
runs, no matter what you pass `render()`.** The two HTML checks that DO run automatically are
the ones `render()` calls directly and separately at the top of the function (`css_var_check`,
`same_as_bg_scan`) — not through the "free preflight" path at all. `antipattern_scan` was never
going to run either way since `preflight` deliberately omits it, but the manual doesn't
distinguish "deliberately excluded" from "silently unreachable through the documented path" —
both read the same from the outside ("nothing printed").

I only found this by opening `engine/build.py` and reading `render()`'s body — nothing in
CLAUDE.md's §7 flags that the convenience path is incomplete, and the brief's own instruction
("pass your gate configuration through `build.render()` rather than calling preflight
separately") reads as if that path is sufficient. It is sufficient for the tuple-based checks;
it is a silent no-op for every HTML-string check except the two `render()` special-cases. I
worked around it by calling the five `layout.*` functions directly (not a second `preflight()`
call, to respect the brief) right before `render()`. That's how v2–v4 caught `invisible_craft_scan`
firing at all — under the documented path it simply would not have run.

## Real bugs the gates caught (all fixed, in order)

1. **v1, hard fail, `invisible_color_check`:** pill fill `var(--bg2)` (`#EDE6D0`) against page
   `var(--bg)` (`#F4EFE0`) measured 19.6 RGB-distance, under the 40 threshold — i.e. the gate
   is right that the FILL alone is indistinguishable from the page. The pill only reads as a
   distinct shape because of its 3px ink border, which the check has no way to see (it checks
   fill-vs-surface color distance only, never geometry/strokes). Fixed by picking a fill the
   gate agrees is a real second surface (`#D9CFAF`, measured 64.5). Worth naming as a genuine
   blind spot: a bordered/outlined shape can be visually fine with near-identical fill, and the
   check has no way to know that, so it will flag legitimate bordered-pill designs every time.
2. **v1, real bug, missed by every hard-fail check:** the footer (`@ngo.aquaterra`) visually
   collided with the bottom pill row — rendered text struck through by the pill's own ink
   border (see the crop in this session: `scratchpad/_crop_footer.png`, now stale/removed).
   `collision_check`'s own `min_overlap=12` threshold measured `oy=12` for that pair — not
   `>12`, so it did not fire. That's not a bug in `collision_check` (its docstring is explicit
   that ≤12px is a deliberate graze allowance for borders), it's that my *declared* footer bbox
   was a guessed constant (`H-70`, height 20) instead of a measured one, and the guess happened
   to land just inside the graze tolerance while the real ink did not. Fixed by measuring the
   footer text for real (`measure_text`) and — more importantly — deriving the pill field's
   `row_bottom_limit` from the footer's real position instead of a second guessed constant.
   This is exactly the class of bug CLAUDE.md §10 already catalogs ("stacked plates spaced by a
   guessed constant clip their own text") — same root cause, different element pair, and the
   existing guard (`reconcile_boxes` under/untracked, `collision_check`) did not generalize to
   catch it because both my declared boxes were self-consistent with each other, just wrong
   relative to reality.
3. **v2, hard fail, `text_contrast_check` (only ran because I added it):** the qualifier line
   on the ink slab used `var(--ink3)` (`#5A5A55`) — measured 2.86:1 against `--ink`, nowhere
   near the 4.5:1 floor. This rendered as a legible-but-weak grey smear (see the pre-fix crop,
   `_crop_qual.png`, also stale/removed) — the kind of thing that reads "fine" in a quick glance
   and fails as soon as you check. I would not have caught this by eye with confidence; the gate
   found it, I picked `#8B8880` (5.59:1) by actually computing `core.contrast()` in a scratch
   REPL rather than guessing a second time.
4. **v3, real bug, no gate catches this class at all:** the ink slab was sized 860×430 while the
   "126" numeral only measures 514px wide (`measure_text`, NeutralFace 900 @ 280px) — leaving
   ~240px of dead flat black inside the one element that is supposed to be the piece's focal
   point. No checker in §7 evaluates "does a container's content actually fill it" as a
   *quality* question (only `contains_check`'s binary fits/doesn't-fits, which this passed
   easily with room to spare). This was caught by looking, per §3, exactly as the manual expects
   — the gate stack does not and cannot replace it here.
5. **v4, polish, not a bug:** CLAUDE.md §9's craft layer explicitly lists "one hero-shine per
   piece" as always-on; nothing in v1–v3 had one. Added a low-alpha diagonal highlight inside
   the slab, painted first in DOM order so text always sits on top of it.

## Gate noise I judged as false-positive / by-design, and why

- `invisible_craft_scan` flagged `('box-shadow', 'var(--bg)', '#f4efe0', 0.0)` on every version
  from v1 on. This is `core.keyline(ring_bg="var(--bg)")` doing exactly what its own docstring
  says: the ring's first segment is deliberately the colour of "whatever the sticker actually
  sits on" (the cream page), so the gap reads as a gap, with the *second* ring (ink) providing
  the actual visible line. `invisible_craft_scan` can't distinguish "outline colour == field
  colour, craft layer vanished" (the bug it exists to catch) from "keyline gap intentionally ==
  field colour, that's the whole mechanism." Every legitimate `keyline()` call will trip this
  advisory. Worth a note in the engine (I did not touch `engine/layout.py` per the brief — this
  is a report, not a patch).
- `reconcile.measure_dom`'s `OFF-CANVAS` fired on essentially every bleeding pill in every
  version (dozens of lines per render). This is `measure_dom` measuring the real, un-clipped DOM
  position — which is correct — for a mechanism (the drawn style's own recipe: "let every row
  bleed off BOTH edges") that is fundamentally, structurally off-canvas by design. It never
  fails a build (only `clipped`/`spilling` get promoted into `issues`), but there is no way to
  tell `measure_dom` "this element bleeding off canvas is intended" — no `bleed=` or
  `intentional_offcanvas=` escape hatch exists anywhere in `reconcile.py`. A style whose whole
  mechanism is edge-bleed will always print a wall of this, with no way to quiet it.
- `reconcile_boxes`'s `BBOX UNDER-REPORTS`/`UNTRACKED` lines (one of each, every version) are
  real instances of the limitation the function's own docstring names ("heavily overlapping
  elements can match the wrong partner... both lists are ADVISORY"): the numeral div, positioned
  inside the rotated slab, happened to land near a now-buried pill's declared origin, so nearest-
  origin matching paired them. I confirmed this by hand (the "drawn 524×289" size is exactly the
  numeral's `ink_w`×`ink_h` from `measure_text`, not anything close to a real pill). Correctly
  advisory, correctly non-blocking, but a caller who didn't already know to check would
  reasonably read "pill_6_1: declared 198×58, drawn 524×289" as its OWN pill being four times
  too small, not as a mismatched match against an unrelated rotated element three rows away.
- `BURIED (advisory)` fired on most pills behind the slab, every version — correct and expected
  (the recipe's whole point is the slab "reads as laid over the pills"), and correctly advisory.

## API surprises

- **`measure_text`'s `line_height` default silently doesn't match your CSS.** I wrote the
  numeral's actual HTML with `line-height:.78` (house style: "every AQ headline" per the
  function's own docstring) but measured it with the default `line_height=1`, because nothing
  prompts you to pass it — the parameter exists (`it.get("line_height", 1)`) but there's no
  warning when your `size`/`weight`/`style` all match the render and `line_height` quietly
  doesn't. Got `h=280` (wrong — matches the render only by coincidence, since 280 is also the
  font-size) instead of the correct `h=219`. Re-measuring with the matching `line_height=0.78`
  gave `ink_h=289`, which is exactly the "BBOX UNDER-REPORTS ... drawn 524×289" figure from the
  reconcile mismatch above — i.e. the tool's own advisory output was quietly telling me my
  measurement call was wrong, several steps removed from where the actual mistake was.
- **`invisible_color_check`'s threshold is calibrated for flat fills, not bordered ones**,
  covered above — not a bug, but a real gap between what it checks and what "visibly distinct"
  means for a house style that outlines everything in 3px ink.
- **`collision_ignore` has to be computed from real geometry, not guessed as a class.** I
  initially considered "ignore every pill-vs-slab pair" as a blanket rule (simplest thing that
  would satisfy the gate), then remembered CLAUDE.md's own container/ignore-pair docs warn
  against exactly this pattern (a whitelisted class hides real bugs). Computing actual overlap
  per pill (a ~10-line loop) was barely more code and is the only version that's actually honest
  about what's declared vs. real.
- **`core.keyline()`/`core.hard_shadow()` compose fine as a comma-joined `box-shadow` list** —
  no surprises here, just noting it worked exactly as documented on the first try, which given
  everything else in this log is worth saying.
- Nothing was a "should have been one call, took ten lines" in the checks I used — the checks
  themselves are all single calls. The ten-line thing was **deriving `collision_ignore` and
  the footer-aware `row_bottom_limit`**, both of which are "read the geometry back out of what
  you just built" problems the engine has no helper for (there's no
  `layout.declared_overlap(a_bbox, b_bbox)` one-liner, so I hand-rolled the same
  min/max-overlap arithmetic `collision_check` already has internally, just to decide what to
  put IN `collision_ignore` before calling it).

## Manual (CLAUDE.md) gaps found

1. **§6/§7 imply `render(..., elements=...)` gives full preflight coverage; it does not**, for
   any HTML-string check (see the big finding above). This is the single most consequential gap
   — it means every bespoke script that follows the "pass everything to render()" convenience
   pattern (which the §6 template itself does NOT do — the template calls `lay.preflight(...,
   html=html, ...)` directly, then renders separately) silently loses five checks. §6's own
   template is actually right; the docstring on `render()` and this task's own phrasing
   ("pass your gate configuration through build.render() rather than calling preflight
   separately") both point away from the template's correct pattern.
2. **Workflow C's checklist (§2) says to run `compare.geometry` on the drawn style's reference;
   `design.py`'s own output already prints overlapping numbers** (`coverage`, `centroid`) with
   no cross-reference to whether that satisfies the step. Ambiguous, not wrong.
3. **No escape hatch, anywhere in the gate stack, for "this element bleeds off-canvas on
   purpose."** `bounds_check` (tuple-world) can be worked around by declaring clipped/visible
   bboxes (what I did — a legitimate, if uncredited, technique), but `reconcile.measure_dom`
   (real-DOM world, auto-run, no opt-out) has no equivalent and will always print a wall of
   `OFF-CANVAS` for any edge-bleed mechanism — and edge-bleed-as-mechanism is literally the
   drawn style I was handed for this brief. If bleed mechanisms are common enough that
   `brain/STYLE_BANK.json` recommends them, this is worth a documented convention (even just
   "expect and ignore OFF-CANVAS spam when your declared elements list already reflects the
   true visible/clipped extents" — one sentence, currently absent).
4. **`invisible_craft_scan`'s interaction with `keyline()` is an unavoidable false positive**,
   not documented anywhere as a known interaction (§10's row for `invisible_craft_scan` only
   discusses the ink-outline-on-ink-field case, not the keyline-gap case).

## Timing / what I had to guess

I didn't instrument wall-clock time per iteration, so these are honest approximations from step
count, not a stopwatch:

- **v1** (first full build): the slow part was not writing the script, it was reading
  `engine/core.py`, `build.py`, `layout.py`, `shapes.py`, `doodles.py` function signatures from
  scratch to know what existed and what each returned — call it the majority of the total time
  for this task. The actual `measure_text`/render cycle itself is fast (`B.session()` amortizes
  the browser cold-start; each render printed near-instantly).
- **v2**: fast — fixing three already-diagnosed issues (fill colour, footer measurement,
  qualifier colour) plus wiring the five manually-called layout functions. Re-render ~seconds.
- **v3**: fastest — one number changed (`SLAB_W`), driven by a single `measure_text` call run
  in an interactive Python one-liner to get the numeral's real width before touching the slab.
- **v4**: fastest — one CSS gradient div added.
- **What I guessed, not measured:** the pill field's row/column geometry (pitch 82px, brick
  offset −90/−170, gap 16px) is hand-tuned by eye against the reference recipe's description,
  not derived from `compare.geometry`'s occupancy grid (see the compare.geometry gap above) —
  I'd call this a reasonable-looking guess that happens to match the reference's grid
  reasonably well in retrospect, not a measured one.
