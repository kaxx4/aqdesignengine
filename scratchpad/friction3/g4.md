## Style draw

`PYTHONIOENCODING=utf-8 python design.py "558 welfare projects logged since 2021" --dept content
--canvas story --ground dark --seed 14` printed a note worth flagging on its own:
`(filters relaxed to find a match: dept=content)`. There is no story+dark+content-judged
reference, so the draw silently (well — printed, not silently) fell back to an unrelated
department's reference (`620d62f101b97c...`, a nightclub flyer). `--dept` therefore only ever
determines the department ACCENT via `core.accent_for()` downstream — it does **not** filter which
mechanism you get if no judged reference matches all four filters at once. That's a real gap
between what the flag *sounds* like it does and what it does; the tool is honest about it
(prints the relaxation) but CLAUDE.md doesn't mention this fallback behavior anywhere in §2's
Workflow C description, so I only found it by reading the printed line and then `stylebank.py`'s
`pick()`.

## §7 gate stack — what I used, and what I only found by reading source

Used essentially the whole opt-in surface in one `B.render(...)` call: `elements`, `color_pairs`,
`page_bg`, `expect_hero`, `collision_ignore`, `text_pairs`, `cascade_stacks`, `contains`,
`containers`, `occlusion`. Plus the manual pixel tier by hand: `preview.report`,
`preview.accent_flood_check`, `ref_metrics.analyze`. Auto-run for free: `css_var_check`,
`same_as_bg_scan`, `audit.audit` (DOM margin/overlap), `reconcile.measure_dom`,
`reconcile.reconcile_boxes`. Not used: `reading_order_check` (no single sentence split across
boxes), `scatter_solve` (only 3 loose doodles — placed and gate-checked by hand instead),
`resolve_label_z` / `rotated_bbox` (no buried-label pile, no rotated element whose footprint
mattered), `antipattern_scan` (no blank-card symptom to chase), `fit_block`/`star_text_width` (no
text-in-a-narrow-waist situation).

Found only by reading engine source, not the manual:

- **`core.on_dark()` / `core.on_ground()` / `core.lit_of()` (`engine/core.py:141-225`) don't exist
  in CLAUDE.md §9 at all.** §9 names `text_on`, `on_cream`, `ink_of`, `accent_for`, `outline_of`,
  `hard_shadow`, `keyline`, `RADII` — nothing about the dark-ground half of the same module, even
  though `on_dark`'s own docstring says "a THIRD of the style bank is dark-ground and every one of
  those builds needs this decision." This is the exact helper the brief's "one AQ accent genuinely
  fails as small type on ink" hint points at (`on_dark`'s docstring: "teal is 4.00:1 and FAILS
  small type"), and I'd have used a hand contrast check without reading `core.py:218-225` end to
  end.
- **`layout.collision_check`'s `containers=` parameter** (`layout.py:118-145`) is mentioned once
  in CLAUDE.md §7a as a one-line bullet ("`ignore_pairs` takes PAIRS...") but the `containers`
  mechanism itself — "a label that HOLDS other elements, so a fully-nested child is skipped
  against THAT container" — isn't described in the manual at all. v1's first `preflight` run
  reported `('cardA', 'num558', 472, 211)` (the hero numeral "colliding" with the card it's
  drawn inside), and my first instinct was to add another `ignore_pairs` entry. Only reading
  `collision_check`'s docstring in full surfaced `containers`, which is the structurally correct
  fix (per CLAUDE.md §7a's own advice to prefer nesting/containment over ignore-listing).
- **One `collision_ignore` argument feeds two *different* label spaces.** `build.render()` passes
  the same `collision_ignore` set to both `layout.preflight()` (which matches against the
  **tuple labels** in your `elements` list) and `audit.audit()` (which matches against the
  **`data-tag` DOM attribute** on `.measure`-tagged elements) — see `build.py`'s `_shoot()`
  calling `audit.audit(html, name, page=pg, canvas=(W,H), ignore_pairs=collision_ignore, margin=M)`
  right next to `layout.preflight(..., collision_ignore=collision_ignore, ...)`. Nothing enforces
  or even flags that these two identifier spaces must line up; it worked here only because I
  deliberately kept my elements'-list labels (`"cardA"`, `"badge"`, ...) identical to the
  `data-tag="cardA"` etc. strings on the actual divs. A silent drift between the two (e.g. a tuple
  labelled `"cardA"` but a div tagged `data-tag="card-a"`) would make the DOM-level ignore a
  no-op while the tuple-level one keeps working, producing `OVERLAP cardA x badge (...)` console
  spam that reads exactly like a real bug. `audit.py`'s own docstring says this in passing
  ("SAME argument the caller already passes to layout.collision_check") but that line lives in
  `audit.py`, not in CLAUDE.md §7's summary or the §6 template.
- **`audit.audit()`'s safe-area margin is hardcoded to `build.py`'s own module constant `M=64`**
  (`build.py`'s `_shoot()`: `margin=M`, not something `render()` exposes as a parameter). My first
  design intentionally bled cards to a ~40-54px margin (matching the reference's measured ~4%
  margins); `render()` gave me no way to loosen that without editing the engine, so v2 tightened
  every edge to the hardcoded 64px instead of the reference's actual measured margin. Not
  necessarily wrong (64px is the house default) but worth knowing it's not configurable from a
  bespoke script, and CLAUDE.md doesn't say so.

## Type colour on the dark field

Every text colour came from a `core` function call, never a literal hex picked by eye:
`GRAPE = core.accent_for("content")` (dept-mandated, `#7E5BFF`), `TXT_ON_GRAPE/TOMATO/LEMON =
core.text_on(<fill>)` for every card's own text (all three happened to resolve to ink,
`#0A0A0A` — measured, not assumed: grape vs ink is `4.55:1`, vs paper `4.35:1`, ink wins by a
hair), `TXT_ON_BG = core.text_on(BG)` for the footer directly on ink (`#FFFFFF`), and
`core.on_dark(<accent>, <size>, True)` for every small decorative doodle sitting straight on the
ink page (heart/sparkle/plus) rather than on a card. `OUTLINE = core.outline_of(BG)` decided the
craft colour once for the whole piece (`#F4EFE0`, cream) rather than per element — I initially
started reasoning per-element (badge on grape vs. on tomato have *different* `outline_of()`
results: `outline_of(grape)` is cream because grape's own luminance is `0.191` (`< 0.22`), while
`outline_of(tomato)` is ink because tomato's luminance is `0.268`), then realised the actual bug
this rule exists to prevent (friendship_day, §10) is about the outline's legibility against the
page ground behind the *whole slide*, and simplified to one token for the piece, which is also
what `layout.invisible_craft_scan` actually checks against (`page_bg`, not a per-element surface).
**I did not pick any colour by eye** — the one time I was tempted (choosing "grape / tomato /
lemon" as the piece's three flat accents) that's a compositional/restraint choice the recipe
explicitly asks for ("exactly three flat colours"), not a contrast decision, so eyeballing which
three hues to use is legitimate; every one of them still went through `text_on`/`on_dark` before
being used as actual type. §9 does *not* make the dark-ground helper easy to find (see above) —
that was the single biggest "read the source, not the manual" cost in this task.

## Manual gaps found (CLAUDE.md)

1. §9's contrast-helper list omits `on_dark`/`on_ground`/`lit_of` entirely (see above) despite
   being exactly the tool a dark-ground brief needs.
2. §9 says the logo is "a pill on dark/photo backgrounds" but `build.logo()` (`build.py:23-25`)
   only ever adds a `drop-shadow` filter when `dark=True` — there is no pill background in the
   helper at all. I hand-built the pill (`background:{core.CREAM};border-radius:999px;padding...`
   wrapping the raw `<img src="{core.LOGO}">`) because the documented behaviour and the actual
   helper disagree.
3. `build.chip()` (`build.py:42-45`) hardcodes `border:3px solid var(--ink)` and
   `box-shadow:4px 4px 0 var(--ink)` with no outline-colour parameter, which is fine on the usual
   cream ground but is exactly the "constant outline colour" anti-pattern §10's bug catalog names
   as the friendship_day defect ("outline colour is a per-slide token ... never a constant"). For
   this piece the chip sits on a lemon fill (ink border is correct there anyway) so it happened to
   be harmless, but the shared helper itself would ship the bug on a chip sitting directly on the
   ink ground. I hand-rolled the chip's markup instead of calling `build.chip()`.
4. §6's template constant `M=64` is presented as *the* margin ("matches build.py's own margin
   constant"), but nothing in §6 or §7 says this same `64` is also the **hardcoded, non-overridable**
   floor `audit.audit()` checks bespoke scripts against via `build.render()` — I only learned this
   by reading `_shoot()`'s call to `audit.audit(..., margin=M)` after v1 printed seven `MARGIN ...`
   lines for elements that were inside my own intended (smaller) safe area.
5. §2 Workflow C doesn't mention that `--dept` on `design.py` can be silently relaxed away from
   the actual style draw (see the style-draw section above) — worth a line since it changes what
   "drew a style with --dept content" actually means.

## API surprises

- **Silent no-op avoided, but confusable output**: `render()`'s `collision_ignore` feeding two
  different label spaces (DOM tag vs tuple label) — see above. Not a bug I hit, but a trap I could
  see myself walking straight into on a script where labels and tags aren't kept in lockstep by
  discipline alone.
- **Gate crying wolf, twice, same root cause**: `reconcile.measure_dom` has no concept of an
  ancestor's `overflow:hidden`. It flags *any* child whose own bounding rect exceeds its parent's
  as `CLIPPED`/`OFF-CANVAS`, even when the parent visibly (and correctly) clips it. Hit this twice:
  - First, cropping a source photo that carries a baked-in caption (`core.PHOTOS["food"]` is a
    finished Instagram post, not raw photography — every image in `core.PHOTOS` has its own
    caption line + small logo watermark baked in, which the manual's "the ONLY real imagery" note
    doesn't warn about). Oversizing the `<img>` via `transform:scale(1.4)` inside a card with
    `overflow:hidden` to push the caption out of frame produced, verbatim:
    ```
    [g4_v3.png] ⚠ CLIPPED cardD: width 590px inside a 492px box — characters are lost
    [g4_v3.png] ⚠ CLIPPED img (by cardD): 94px past its container's left edge — content is cut off
    [g4_v3.png] ⚠ CLIPPED img (by cardD): 94px past its container's right edge — content is cut off
    [g4_v3.png] ⚠ CLIPPED img (by cardD): 225px past its container's bottom edge — content is cut off
    [g4_v3.png] ⚠ OFF-CANVAS img: box (402,734)-(1090,1535)
    ```
    even though the actual screenshot showed the crop working exactly as intended (verified by
    rendering and looking — the caption was gone, nothing visibly leaked past the card). Rather
    than ship a "finished" render whose own gate output reads as broken, I found a different fix
    that doesn't trip the check at all: at a fixed box **width**, `object-fit:cover`'s internal
    scale is fixed regardless of box **height** (`1350 * 500/1080 = 625px` tall here, always), so
    box height is a free lever for more natural crop with zero DOM overflow — shortened
    `CARD_D` from 580px to 460px and dropped the `transform` entirely. Zero clip warnings, same
    visual result.
  - Second: adding a "hero-shine" craft highlight (CLAUDE.md §9's "one hero-shine per piece") as a
    rotated, intentionally-oversized gradient div clipped by its card's `overflow:hidden`
    reproduced the *exact same class* immediately: `CLIPPED div (by cardA): 108px past its
    container's left edge`, `OFF-CANVAS div: box (-44,134)-(440,734)`. Confirms this is a general
    limitation of the check, not a one-off — any "oversize + rotate + let the parent's
    overflow:hidden crop it" technique trips it, regardless of what's inside the div (photo or
    plain gradient). Fixed by getting the same diagonal-sweep look from a same-size
    `linear-gradient(125deg, ...)` background instead of a rotated/oversized element — no
    element geometry exceeds its own box, so nothing to flag.
- **Gate silent on something real, briefly**: `preview.critique`'s `flat_dominant` check
  (`>52%` one flat colour) fired on v1-v3 (`fill=0.46 ... one flat color >52% — break up the
  field`) purely because the **ink page background** occupied >52% of the canvas — which is not a
  defect on a brief that explicitly forces `--ground dark`. CLAUDE.md §4 documents an *escape
  hatch* for exactly this shape of false positive, but only inside Workflow A's
  `ARCHETYPE_PROFILES` ("giant_type's dark base is an intended signature... exempt"). Workflow C
  bespoke scripts have no equivalent registry — the call is left entirely to human judgement with
  only a print statement, no data-driven adjustment. I didn't special-case it; I treated the
  *other* half of the same report (`quads={'BL': 0.34, 'BR': 0.33}` vs `'TL': 0.61, 'TR': 0.55}`)
  as the real, ground-agnostic signal (a spatial fill measure, not colour-dependent) and scaled up
  existing decoration until both the quadrant imbalance and the `flat_dominant` trigger cleared
  together (v4: `fill=0.48`, `quads` up to `.40/.38`, verdict flips to `PASS`) — i.e. the
  colour-based check turned out to be a symptom of genuinely being too sparse, not a false alarm
  I had to suppress.
- **A metric that inverts completely on a dark-ground piece**: `ref_metrics.analyze()`'s `vdr`
  proxy is built on `darkmask=(lum<90)` (`ref_metrics.py:32`) — a heuristic for "how much of the
  canvas is headline ink on a light page." On this piece it returned `vdr=0.99` (manual's own
  target range is `0.06–0.20`, ">0.22 = headline swallows the piece") and `ink=0.596` (manual
  target `~0.11`) — both wildly out of range not because the composition is broken but because the
  **entire ink page ground** satisfies `lum<90` just as much as real headline ink does, so the
  "dominant dark blob" bbox the proxy computes is essentially the whole canvas. CLAUDE.md's only
  documented `ref_metrics` caveat is the *opposite* failure ("flat-vector recreations read low on
  vdr vs gradient/photo references") — this is a bigger, undocumented inversion in the other
  direction, specific to any predominantly-dark-ground original. I did not chase this number; I
  verified hero dominance visually and via the (ground-agnostic) `layout.dominance_check`
  (`expect_hero=True`, hero card is 16.5% of canvas, clears the 12% floor) instead.
- **Confusing return, not a bug**: `reconcile.reconcile_boxes`'s "BBOX UNDER-REPORTS" advisory
  persisted for the hero numeral across all 4 versions even after padding the declared box by
  8-20% (`declared 472x211, drawn 459x258` in v1 → still off after padding). Root cause I could
  verify: `measure_text`'s canvas-based `glyph_w/glyph_h` doesn't account for the CSS
  `letter-spacing` applied on the real div (canvas `measureText` ignores it), so a numeral set at
  `letter-spacing:-4px` measures narrower via canvas than it paints via CSS layout width in one
  axis, while `line-height:.78` inflates the *other* axis in the actual DOM box beyond what the
  glyph-only metric reports. Both are real, separate small gaps in what `measure_text`'s
  docstring promises ("the TRUE painted glyph box") vs what it can measure (glyph-only, no
  spacing/line-height applied) — worth a line in the docstring since the fix (pad by a guessed
  %) is exactly the "sized by guess" anti-pattern §6 says `measure_text` exists to retire, and
  here it couldn't fully retire it. Advisory only, never blocked a render.
- **A one-time real trap, mine not the engine's**: `text_pairs += [...]` inside `async def
  build():` throws `UnboundLocalError: cannot access local variable 'text_pairs'` the moment
  Python sees an assignment target with that name anywhere in the function body — needed
  `global elements, color_pairs, text_pairs` at the top. Not an engine bug, but the §6 template's
  own shape (module-level `elements = []`, appended to from inside helper code) invites exactly
  this the moment the actual build logic has to live inside an `async def` (which it does, the
  moment you need `await B.measure_text(...)` before laying anything out) and the template
  doesn't call this out.

## Iteration notes / what was guessed

- **v1** (design.py draw, `compare.geometry` on the reference, first bespoke build): built the
  4-card diagonal fan from hand-worked-out overlap geometry (~20% overlap per pair, computed by
  hand against `cascade_peek_check`'s back-to-front convention before ever running the gate, then
  confirmed by running it) — this part worked first try. What didn't: didn't anticipate that
  `CARD_A`'s width would eat 84px into `CARD_B`'s own bbox and that `CARD_B`'s inner stat text
  (left-padded from `CARD_B`'s own edge, not from the overlap-adjusted edge) would land inside
  that shared zone, colliding with both the badge and the numeral under `cardA`. Six collisions,
  seven margin breaches (all `x<61` or `right>1019` against the hardcoded 64px audit margin I
  hadn't found yet), two DOM overlaps. All diagnosed from one preflight+audit run and fixed in v2.
- **v2**: added `containers=["cardA","cardB"]`, four more explicit `ignore_pairs`, moved every
  edge coordinate to respect the 64px floor, re-padded the numeral bboxes. Gates went fully clean
  first try after those changes. This is also where I looked at the actual PNG for the first time
  and caught the real defect no static gate could see: the food photo's baked-in caption bleeding
  into the card, half-legible ("STANDING STEADFAST FOR THE" then cut off mid-sentence).
- **v3**: fixed the caption bleed (two attempts — oversize+transform first, reverted for the
  `reconcile` false-positive above, then the box-height approach), renamed a repeated "FIELD LOG"
  eyebrow that read as a copy-paste mistake, added a 3-doodle cluster to fill the bottom-half gap
  `under_filled_quadrants` had been advisory-flagging since v1 (`[2,3]`, i.e. both bottom
  quadrants, every version so far).
- **v4**: `preview.report` showed the cluster was correctly *placed* but too small
  (`BL:0.34/BR:0.33` bottom vs `TL:0.61/TR:0.55` top, and `flat_dominant` still firing at
  `fill=0.46`) — scaled the three doodles up (~30-35% bigger each) and enlarged/repositioned the
  ellipse callout, which cleared both. Added the hero-shine (hit and fixed the second
  `reconcile` false-positive, see above). Added `occlusion_check` wiring as the last unused
  applicable §7a check. Final gate run: `preflight CLEAN`, `margins/overlap CLEAN`, `RENDER
  ISSUES: []` (two harmless advisory "BBOX UNDER-REPORTS" lines on the doodle icons, root cause
  not fully chased — likely `reconcile`'s selector measuring the inner `<svg>`'s own rect rather
  than the wrapping div, given the size delta is consistent across doodle kinds).
- Nothing in the final piece was sized by a bare guess with no measurement behind it — every
  text block went through `measure_text` first, every colour through a `core` contrast function,
  every overlap through `cascade_peek_check`/`collision_check` before being trusted. The one
  deliberately-eyeballed choice was aesthetic restraint (which 3 accents to use, where to place
  3 filler doodles within a gate-verified free zone), which is a taste call the manual asks for,
  not a measurement the engine can make for me.
