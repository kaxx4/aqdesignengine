## RE-PROPORTION guidance: never actually exercised

The drawn style's own judged `canvas` is `square`, and the reference file itself is a 736x736
square JPEG. `stylebank.brief()`'s `canvas_shift()` returns `None` when the target canvas equals
the style's own canvas, so **no RE-PROPORTION block printed at all** — there was nothing to
re-solve. I read `canvas_shift`/`brief()` in `engine/stylebank.py` (lines 265-329) directly to
confirm this rather than assume, and separately ran `compare.geometry()` on the reference myself
(Workflow C step 0) to get real numbers: `content_bbox 0.000..0.998 / 0.000..0.999`, `coverage
0.883`, essentially zero outer margin on every side.

So I can't tell you whether the RE-PROPORTION guidance text (which I read cold, since it never
printed for me) is *sufficient* when it actually fires — my draw got lucky and never needed it.
What I can say: the guidance exists as a wall of prose in `brief()` ("TRANSFERS as written: the
mechanism... DOES NOT TRANSFER: coverage, centroid and content_bbox... Re-solve the layout for
your frame") with no worked numeric example, so a builder who *does* hit a portrait→square shift
still has to invent their own re-solved coordinates from words alone, same as I did for the
un-shifted case. I'd treat "the guidance was usable" as unverified by this run, not confirmed.

One deliberate deviation worth flagging honestly: the reference is genuinely zero-margin
full-bleed (`coverage 0.883`, `margins L0.000 R0.002 T0.000 B0.001`). I did **not** build to
that — I used AQ's standard `M=64` safe margin throughout, because `audit.py`'s own MARGIN check
(see below) would flag near-edge content on any element I tag `class="measure"`, and because
every other AQ poster in this repo uses the same margin convention. This is a considered
"acceptable adaptation" (house margin discipline over literal reference proportion), not an
oversight, but CLAUDE.md's Workflow C checklist ("build to its proportions") doesn't say which
wins when the reference's own measured proportion actively fights the brand's own gate.

## The one real defect only the eye caught

Every automated check passed clean on what became v5 (`preflight CLEAN`, `audit margins/overlap
CLEAN`, `reconcile` showing only two low-priority advisories). I then actually `Read` the PNG (the
looking gate, §3) and the footer credit line, `@ngo.aquaterra`, was **functionally invisible** —
cream text sitting mostly on the plain cream page background, not on the photo/scrim it was
colour-picked for. Cropping the render confirmed it: only the last couple of characters clipped
onto the photo's edge; the rest was cream-on-cream.

The cause: I placed the handle at `x=M` (64) and passed `text_pairs.append(("handle_text",
core.CREAM, "#241b12", 15, True))` — asserting the surface behind it was the photo's dark scrim.
It wasn't; the photo starts at `x=230`, so most of a 236px-wide handle at `x=64` sits on the
page. `text_contrast_check` passed because *I told it* the surface was `#241b12` and cream on
`#241b12` genuinely does clear 4.5:1 — the check did its job correctly against the input I gave
it. Nothing in the stack cross-checks a declared surface against what is actually geometrically
behind an element the way `same_as_bg_scan` auto-infers the *page* background from the page's own
CSS. That auto-inference exists for the page bg specifically; it has no equivalent for "the
surface behind element X specifically," which is exactly the gap that let this ship. Fixed by
moving the handle onto the photo itself (`x = photo_x + 24`). This is the session's cleanest
demonstration of CLAUDE.md §3's actual claim — that metric/DOM checks are proxies and the
rendered PNG is the only reliable check — because every proxy genuinely was clean.

## API surprises

**1. `audit.py`'s `ignore_pairs` and `layout.collision_check`'s `elements` labels are two
different namespaces, silently.** `render()`'s `collision_ignore` argument is documented as "the
SAME argument the caller already passes to layout.collision_check" (`engine/audit.py` line 25-26)
— true, but it is matched against `data-tag` HTML attributes in `audit.py`, while
`layout.collision_check` matches it against the labels in the `elements` tuple list. In v1 I gave
all three headline plates `data-tag="plate"` (thinking of it as a category, the way `build.py`'s
own `chip()`/`doodle()` helpers use `data-tag="chip"`/`"doodle"`), while my `elements` labels were
unique (`"tag"`, `"num"`, `"workshops"`). Result, from the *same* `collision_ignore` argument, in
the *same* render call:
```
[preflight] ISSUES:    (no "collisions" line — layout.collision_check matched fine)
[g2_v1.png] ISSUES:
   - OVERLAP plate x plate (267x31px)
   - OVERLAP plate x plate (666x60px)
```
Two gates that are supposed to cooperate on one ignore-list disagreed, from one input, for a
reason that is invisible unless you already know `data-tag` is a second bookkeeping surface.
Fixed by giving every plate a `data-tag` equal to its `elements` label.

**2. `audit.py`'s `MARGIN_OK` is a closed set with no parameter to extend it.** Line 10:
`MARGIN_OK={"note","key","flyer","we","won","tb","title","body"}`. My photo intentionally touches
the canvas's bottom edge (`bottom == H` exactly, a deliberate anchor). Tagging it `class="measure"
data-tag="photo"` got:
```
[g2_v2.png] ISSUES:
   - MARGIN photo breaches safe area (x230 r850 b1080)
```
Unlike `ignore_pairs` (which session 10f's own comment says was made caller-extensible for
exactly this class of "legitimate by-design" case), there is no equivalent parameter for margin
exemptions. The only fix available to a Workflow-B/C author who can't touch `engine/*.py` is to
not give that element `class="measure"` at all — which works, but silently opts it out of the
overlap check too, not just the margin one. I did this (see the comment in `g2_v3.py`/`g2_v5.py`)
and it is a real gap in what the gate stack can express, not a design flaw in my poster.

**3. `reconcile.measure_dom`'s default `bleed_tags=("num","bleed","hero-bleed")` collides with an
ordinary element name.** I originally called my hero numeral's plate `"num"` (a completely
natural name for a numeral plate). `engine/reconcile.py` line 142's default bleed-tag whitelist
happens to contain exactly that string, for reasons unrelated to naming a numeral — it would have
silently exempted my numeral from the off-canvas check the moment it (hypothetically) ever went
off-canvas, for a reason that has nothing to do with an intentional bleed. Renamed to `"hero_num"`
once I noticed the collision by reading `reconcile.py` source; nothing would have told me this
otherwise.

**4. Achieving a genuine full-bleed element is impractical under the current stack without
touching engine source.** `reconcile.py`'s selector (line 132) now measures "every positioned
descendant," not just `.measure`-tagged ones (a deliberate fix, per the comment at line 123-131,
for elements hiding via legitimate nesting). But that means a bled element's *every internal div*
needs its own `data-tag` in `bleed_tags` to avoid an OFF-CANVAS report — and helper functions like
`tex.duotone()` return a self-contained HTML string with no parameter to inject a `data-tag` into
their internal `inset:0` wrapper divs. In v1 I bled the photo 120px past the bottom edge and got:
```
[g2_v1.png] ⚠ OFF-CANVAS div: box (230,640)-(850,1200)
[g2_v1.png] ⚠ OFF-CANVAS div: box (235,645)-(855,1205)     (x4 more, one per internal duotone/scrim div)
[g2_v1.png] ⚠ OFF-CANVAS img: box (235,645)-(855,1205)
```
I worked around this by not bleeding the photo at all (fully contained, `bottom == H`) — an
acceptable adaptation for this piece, but a real capability gap: CLAUDE.md presents full bleed as
a normal, encoded-for move ("full bleed is a real AQ move" — `reconcile.py` line 154's own
comment), yet doing it cleanly through a texture helper is not actually supported end to end.

**5. `shapes.fit_font`'s `fits=True` does not mean "legible," just "≥ min_box."** Default
`min_box=5.0`, `max_box=15.0` (lines 430-458). For my first badge attempt (two lines, "HANDS-ON" /
"LEARNING" in a 230px starburst) it returned `box≈6.86, fits=True` — which back-converts to about
16px of actual rendered text in a 230px badge. That is not shippable type by CLAUDE.md's own
"never ship 5pt type" standard, but the function's own success flag says otherwise. I caught this
by hand-converting box units to px myself before trusting it (see `scratchpad/_measure_probe2.py`)
and simplified the badge to a single short word ("LABS") that fits comfortably (~32px) instead.
`fits` answers "does *some* box-unit size clear the floor," not "is the result actually legible" —
worth knowing before trusting it as a pass/fail gate on its own.

**6. The padding chase (`reconcile_boxes` "BBOX UNDER-REPORTS") is a fixed point, not a one-shot
fix.** Padding `hero_plate`/`ws_plate` to close a ~24px under-report grew their *declared* boxes,
which shifted where their neighbours needed to sit to avoid a new collision, which I then had to
re-solve by hand:
```
v2: preflight CLEAN, but reconcile: "BBOX UNDER-REPORTS hero_plate: declared 702x354, drawn 714x378"
v3: (padded) -> "collisions: [('ws_plate', 'photo', 620, 19)]"   (new collision from the padding)
v4: (moved photo down) -> "collisions: [('ws_plate', 'photo', 620, 13)]"  (padding grew AGAIN, same fight)
v5: (moved photo down further, shrank it to compensate) -> preflight CLEAN
```
Nothing documents that closing this advisory can cascade into new hard-fail collisions on
adjacent elements; I found out by doing it.

## Manual (CLAUDE.md §7) gaps found only by reading source

- `layout.text_contrast_check` / `render(text_pairs=...)` — **not mentioned anywhere in §7**,

  by reading `layout.preflight`'s actual parameter list.
- `layout.reading_order_check` / `render(reading_order=...)` — **not mentioned anywhere in §7**.
  This is the single sharpest check I used this session (see the column-trap bug below) and the
  manual doesn't know it exists.
- `layout.img_src_check` — **not mentioned in §7** (auto-run inside `preflight` whenever `html=`
  is passed).
- `layout.double_rotation_scan` — **not mentioned in §7** (auto-run, advisory).
- `render()`'s actual signature takes `collision_ignore, containers, text_pairs, cascade_stacks,
  reading_order, contains, occlusion, auto_nudge` — §6's template only shows the older
  `elements=, color_pairs=, page_bg=, expect_hero=` subset. I found the rest by reading
  `engine/build.py` lines 147-150 directly, which is also exactly what my task instructions told
  me to route my gate configuration through.

`reading_order_check` finding, concretely, because it's the best evidence the check pulls its
weight: my v1 headline stack was `tag_plate x=150`, `hero_num x=90`, `ws_plate x=135`. It printed:
```
COLUMN TRAP: 'tag' and 'workshops' share a left edge (x=150 / x=135) with 'num' (x=90) between
them — they will read as a column, so the sentence scans 'tag' -> 'workshops' -> 'num'
```
This is real: 150 and 135 are 15px apart (within the 24px tolerance), 90 is not, so the eye's
alignment-seeking would genuinely have skipped the hero numeral. I would not have caught this by
looking at the render casually — it's a sub-perceptual alignment coincidence, not an obvious
error — and it is exactly the kind of thing CLAUDE.md's own bug catalog says only the eye used to
catch (the "showing / and again / up again" precedent this check was built from). Fixed by moving
`ws_plate` to `x=110` (40px from `tag_plate`, clearing the tolerance).

## Top 3 friction points

1. **Two silent namespaces for "ignore this overlap"** — `audit.py`'s `data-tag`-keyed
   `ignore_pairs` vs. `layout.collision_check`'s `elements`-label-keyed one — share one caller
   argument and one docstring claim ("SAME argument"), but only work together if the author
   independently keeps `data-tag` and `elements` labels in lockstep, which nothing enforces or
   documents.
2. **CLAUDE.md §7 is stale against the actual `layout.py`/`build.py` API.** `text_contrast_check`,
   `reading_order_check`, `img_src_check`, `double_rotation_scan`, and half of `render()`'s real
   parameters exist in code and are wired into `preflight`, but are simply absent from the manual
   I was told to treat as the operating manual. `reading_order_check` in particular is the
   sharpest, most genuinely eye-replacing check I used all session, and it isn't mentioned once.
3. **Full-bleed elements are "a real AQ move" in comments but not actually well-supported**: no
   `MARGIN_OK` extension point, and texture helpers (`tex.duotone`, etc.) give a bled element's
   internal children no way to carry the `data-tag` the off-canvas exemption needs. I ended up not
   bleeding the photo at all, which is an acceptable adaptation for one poster but means the
   documented "full bleed is normal" story doesn't hold up mechanically for a Workflow C author
   who can't edit `engine/*.py`.
