## 1. Where the docs were wrong, stale, ambiguous, or missing a step

- **`shapes.sticker()` silently assumes a SQUARE silhouette and CLAUDE.md's §6 template doesn't
  say so.** `sticker()`'s viewBox line is `vb = f"{-pad} {-pad} {box + 2*pad} {box + 2*pad}"`
  (shapes.py:513) — always `box x box`, regardless of the path's actual coordinate extents. I
  tried using it for the 5 capsule pills (`shapes.capsule(w=300, h=64)`, a path drawn in a
  300x64 space) and the pill would have rendered almost entirely outside a 100x100-assumed
  viewBox. Nothing in CLAUDE.md §6/§9/§10 or the RECREATION_PROTOCOL warns that `sticker()` only
  works for near-square silhouette families (scallop/starburst/gear/blob/shield are all
  radially symmetric; `capsule`/`wave_banner`/`tag` are not). I ended up building the 5 pills as
  plain bordered `<div>`s instead, matching the reference's flat, shadow-less look exactly, and
  treating "cream fill + ink outline, uniformly" (the actual INTENT of RECREATION_PROTOCOL rule
  2) as satisfied by the visual result rather than by literally calling `sticker()` on every
  object. This should be a documented caveat on `sticker()`, not something the next builder
  finds by reading the source after typing `capsule(300, 64)` and getting a garbled render.

- **A genuinely new, undocumented bug class: `.dood{z-index:4}` + a wrapper `transform` creates
  an invisible-under-a-sibling failure that no existing catalog row covers.** `build.page()`'s
  global CSS (`build.py:65`) sets `.dood{position:absolute;z-index:4}` on every doodle SVG. I
  stacked a `heart` doodle and a `lightning` doodle to build a "broken heart" (tomato heart +
  black lightning crack). The heart's wrapper div had no `transform`, so its z-index:4 escaped
  into the shared ancestor stacking context. The lightning's wrapper div had
  `transform:scale(0.72) translate(8px,-4px)` (my own choice, for a small offset) — a
  `transform` on an element creates a NEW stacking context per the CSS spec, so the lightning's
  z-index:4 got trapped inside that isolated context, and the WHOLE subtree only competed at
  z-index:auto(0) against the escaped heart at z=4. 0 < 4, so the lightning painted invisibly
  underneath, in an otherwise `preflight`-CLEAN render. I only found it by the looking gate (Read
  the PNG) — no static or DOM check flagged it; `reconcile.measure_dom` doesn't reason about
  paint order, only extents. CLAUDE.md §10's bug catalog has rows for "doodle nested in a
  bespoke art svg inherits the parent viewBox" and "z-index escapes stacking context" is a
  distinct, equally silent failure mode of the SAME `.dood{z-index:4}` global rule, and it isn't
  in the catalog at all. I fixed it locally (explicit z-index on both wrappers) but this is
  exactly the kind of thing §8 says should get written back as a rule/self-test — I did not do
  that myself (out of scope for a bespoke Workflow-B script per my brief: "don't edit
  engine/*.py"), so I'm flagging it here for whoever owns §10 next. Minimal repro kept at
  `scratchpad/friction4/_repro.png` and the reasoning that produced it.

- **`render()`'s `collision_ignore` is silently overloaded with two incompatible semantics, and
  the resulting warning is unavoidable noise on every bespoke script.** `layout.collision_check`
  (the tuple-list world) matches ignore-pairs against your element LABELS. `audit.audit()` (the
  DOM world, also invoked inside `render()`/`_shoot()`) matches ignore-pairs against `data-tag`
  attributes on actual DOM elements. Passing the SAME `collision_ignore` set to `render()`
  forwards it to BOTH, and since my elements never had `data-tag` (bespoke scripts don't, by the
  §6 template), every single render printed: `IGNORE PAIRS NAME NO data-tag IN THE DOM: [...] —
  this gate matches data-tag, while layout.collision_check matches your element LABELS. Tags
  present: []`. It's harmless (audit's own margin/overlap check reported CLEAN regardless), but
  it fired on all 9 of my renders with no way to silence it short of tagging every div with a
  matching `data-tag`, which the template doesn't ask for. CLAUDE.md §7b documents `audit.audit`
  and §7a documents `collision_check` as separate things, but never says they share one
  parameter name with different matching rules — I found this by reading `build.py`'s
  `_shoot()`/`render()` source, not from the manual.

- **`scatter_solve` has exactly one `max_pair_overlap` per call, and nothing in its docstring or
  CLAUDE.md §7a warns that a single ceiling cannot serve two object types with genuinely
  different overlap tolerance.** A sticker's whole design (repeated "Drag me" ring text,
  redundant illustration) can absorb 30-40% overlap and still read fine. A pill's ENTIRE box is
  its one-shot, non-redundant label — any serious overlap clips a WORD. I hit this directly:
  `max_pair_overlap=0.38` on one shared call let "LINKEDIN" render as "LINKED" behind the
  DRIBBBLE pill (`resolve_label_z` correctly flagged it `UNRESOLVED`). The fix (splitting into
  two `scatter_solve` calls — stickers first, then pills with the stickers passed as `protect`
  at a low `max_protect_cover`) works, but it's an architecture decision the tool gives you no
  hint you'll need until you've already shipped a clipped word. Worth a line in the docstring:
  "if your pile mixes redundant-content objects (stickers/badges) and single-shot-label objects
  (pills/tags), place them in separate calls with different overlap ceilings."

- **§9's logo rule doesn't anticipate recreating a reference whose wordmark has NO pill/card at
  all.** "Logo — a pill on dark/photo backgrounds; NEVER white-inverted" reads as unconditional,
  but the reference here is raw tracked text directly on black, no card, no icon. I judged that
  faithfully recreating the reference's actual mechanism (a typographic name-mark) outranked
  applying the pill rule to a bitmap logo that isn't what the reference shows, and used AQ
  wordmark TEXT directly on ink instead of `core.LOGO` + a pill. This is a genuine ambiguity
  CLAUDE.md doesn't resolve: is §9's pill rule about the brand asset (`core.LOGO`, the bitmap)
  specifically, or about "AQ's identity mark" in general (which would then also cover a
  typographic substitute)? I made a call and documented it in `RECREATION_AUDIT.md`; a future
  reader should not have to re-derive the same judgment call from scratch.

- **`runqueue.py record`'s status model has no state for "looking gate passed clean, score is
  marginally over the line."** The task brief explicitly says "do NOT accept on score alone,"
  which implies a looking-gate-driven acceptance path should exist independent of the number.
  But `record` computes `status = "done" if score <= accept_score else "attempted"` with nothing
  in between — there's no way to record "this recreation is genuinely finished, the residual
  score gap is a metric-sensitivity artifact, not a fidelity defect" as anything other than a
  prose note buried in the `note` string. (A concurrent agent working a different slug in this
  same session hit the identical wall and wrote almost the same complaint independently in
  `RECREATION_AUDIT.md` around line 2500 — two agents finding the same gap without coordinating
  is a decent signal it's real, not a one-off misunderstanding.)

## 2. Dark-ground type colour — exactly how each one was decided, and whether §9 made it easy

§9 names the right entry points (`core.on_dark`, `core.outline_of`) and they were easy to FIND —
the friction is that the manual just points at the measurement, it doesn't hand you the numbers;
you still have to run the function yourself, which is presumably intentional ("measured, never
assumed"). I ran this diagnostic before building anything:

```
contrast(CREAM, INK) = 17.22     contrast(PAPER, INK) = 19.80
pink   #FF4D8C  on_dark@16px -> #FF4D8C (unchanged, raw contrast 6.31 vs ink)
mint   #1B8A5A  on_dark@16px -> #1B8A5A (unchanged, raw contrast 4.55 — JUST clears AA_NORMAL 4.5)
lemon  #FFC700  on_dark@16px -> #FFC700 (unchanged, raw contrast 12.65)
tomato #FF4D2E  on_dark@16px -> #FF4D2E (unchanged, raw contrast 5.99)
sky    #3DA9FC  on_dark@16px -> #3DA9FC (unchanged, raw contrast 7.81)
grape  #7E5BFF  on_dark@16px -> #7E5BFF (unchanged, raw contrast 4.55 — JUST clears)
teal   #0E7C86  on_dark@16px -> #268992 (TINTED — raw contrast 4.00, FAILS AA_NORMAL, on_dark tints it)
outline_of(CREAM) -> #0A0A0A (ink)      outline_of(INK) -> #F4EFE0 (cream)
```

So teal is the one accent that fails as small type on ink, exactly as the brief said — confirmed
by running the function, not by reading a table anywhere (there isn't one for `on_dark`; the
`ACCENT_INK` table in `core.py` is for the CREAM-ground case only, so the ink-ground numbers had
to be computed fresh).

Applied:
- **Footer contact line** (`text_on(INK)` scenario): `core.text_on(INK)` literally returns
  `PAPER` (#FFFFFF, 19.80:1). I used `CREAM` (#F4EFE0, 17.22:1) instead — a deliberate override
  of the function's own answer, not a by-eye guess: I computed `core.contrast(CREAM, INK)`
  myself first to confirm it still clears AA_NORMAL by a wide margin (17.22 vs the 4.5 floor)
  before overriding, on the grounds that pure white text is off-brand for AQ (CLAUDE.md is
  explicit elsewhere that the page ground is "cream, NEVER white" — I extended that spirit to
  foreground type on a dark ground too, which the manual doesn't explicitly say one way or the
  other).
- **Cross/plus ornament stroke colour**: `core.outline_of(INK)` -> CREAM. This is the one place I
  used the helper exactly as documented (craft-on-a-field decision), and it's correct: an ink
  ornament on an ink ground would have been the exact "invisible craft layer" bug CLAUDE.md's bug
  catalog already tracks for a DIFFERENT context (outline+shadow on a matching field) — same root
  cause, different element type.
- **Wordmark flourish dot**: `core.on_dark(PINK, 18, bold=True)` -> unchanged (pink already clears
  4.55+ at that size). This is the one spot I genuinely exercised "pick the accent, ask the
  function whether it survives, act on the answer" for a real (if small/decorative) design
  choice, not just a diagnostic run.

**What I picked by eye, honestly:** the wordmark/pill/footer font FAMILIES (mono for the eyebrow,
NeutralFace-weight-900 for pill labels, Eina for the footer) — there is no measured helper for
"which font register reads as the reference's tracked serif small-caps," that's a judgment call
CLAUDE.md leaves to taste, correctly. The illustration accent hues (mint for the hand, pink/tomato
for the two hearts) were also picked by eye from `core.ACCENTS`, not measured — there's no
contrast requirement for a decorative fill against a light sticker card, so there was nothing to
measure.

## 3. `scatter_solve` / `resolve_label_z` — usable, but not out of the box

Never hand-placed final coordinates — every pile position in v6 came out of `scatter_solve`. But
getting there took real architecture work the tool doesn't hint at:

- **One global `max_pair_overlap` doesn't fit a mixed pile.** Documented above (section 1). Fix
  was two sequential `scatter_solve` calls (stickers, then pills against stickers as `protect`),
  which IS within the tool's documented vocabulary (`protect` vs `keep_out` are both real,
  documented parameters) but the NEED for two calls instead of one is not documented anywhere.
- **`scatter_solve`'s honest-failure mode (`unplaced`) is real and fired twice** (v5:
  `['behance','dribbble']` unplaced with an over-tight zone + keep_out + low overlap all at once;
  v5-retry: `['heart','instagram','behance','dribbble']` unplaced when I also lowered
  `max_pair_overlap` further). This is GOOD — it did exactly what its docstring promises
  ("anything that could not be placed... comes back in `unplaced` rather than being dropped
  somewhere bad") and I had to loosen constraints and re-run rather than get a silently broken
  render. But it means the practical workflow is "guess constraints, get an unplaced list, loosen,
  repeat" — there's no solver diagnostic telling you WHICH constraint was the binding one (was it
  the zone size, the keep_out block, or the overlap ceiling?), so the loosening is trial and error.
- **`resolve_label_z` genuinely caught two real bugs I would have shipped blind otherwise**: the
  "LINKED" clipping (v5, flagged `UNRESOLVED: ['instagram','linkedin']` then later
  `['instagram']`) and confirmed clean on v6 (empty unresolved list, verified against the actual
  render — no clipped words). This is the single most useful check in the whole pass; it is doing
  something no other §7 check can do (protecting a LABEL sub-box inside an object that is
  deliberately, heavily overlapped).
- **A real false-positive from `collision_check` on circular objects**: `('tongue',
  'heart_illustration', 17.02, 74.8)` fired even though the two STICKERS (`tongue`, `heart`)
  were correctly overlap-exempt and do not visually touch at all (confirmed by eye — there's a
  clear black gap between them in the render). Root cause: a circular sticker's declared bbox is
  its bounding SQUARE (per `shapes.sticker()`'s own docstring: "the rendered box is ALWAYS size x
  size, SQUARE"), so two adjacent circles' square CORNERS can overlap on paper with zero real ink
  touching, and anything nested inside one sticker (the illustration) inherits that same
  false-positive risk against every OTHER pile object, not just its own parent. I fixed it by
  adding every illustration to the same blanket `collision_ignore` as the pile objects themselves,
  but the underlying cause (square bbox for a circular shape) is a structural property of
  `shapes.sticker()` that CLAUDE.md doesn't call out as a collision-check caveat anywhere.

## 4. APIs that surprised me (recap of the load-bearing ones, in order of severity)

1. `.dood{z-index:4}` (build.py:65) interacting with a sibling wrapper's `transform` to make a
   doodle invisible regardless of DOM order — section 1, the worst one, caught only by eye.
2. `shapes.sticker()`'s forced-square viewBox silently mis-rendering non-square silhouettes.
3. `collision_check`'s bounding-square treatment of circular objects producing a real false
   positive against nested content.
4. `render()`'s `collision_ignore` forwarding to two checkers with incompatible key semantics
   (label vs. `data-tag`), producing unavoidable noise.
5. `reconcile.measure_dom`'s advisory line `BBOX UNDER-REPORTS tongue_illustration: declared
   89.08x89.08, drawn 204x62` — never fully diagnosed (advisory, not blocking, and I ran out of
   iteration budget chasing it). 204x62 is a very different aspect from the declared 89x89 square,
   which makes me suspect it measured the sticker's OWN inner "Drag me" arc-text `<text>` element
   (also part of the same `<svg>`, inserted via `sticker(..., inner=text_on_arc(...))`) rather
   than the illustration div I actually declared — but I did not confirm this, and am reporting it
   as an open question rather than a diagnosed bug.

## 5. Gates that fired on nothing, and the one gate that stayed silent on something real

**Fired on (essentially) nothing, every single render:**
- `IGNORE PAIRS NAME NO data-tag IN THE DOM` — section 1, cosmetic noise, 9/9 renders.
- `invisible_craft (advisory): [('border', '#0A0A0A', '#0a0a0a', 0.0)]` — fired IDENTICALLY on
  all 9 renders regardless of what changed in the composition. This is my pill borders: ink
  border on a CREAM pill (correct, per `outline_of(CREAM)=INK`), but `invisible_craft_scan`
  appears to compare the border colour against the PAGE ground (ink) rather than the pill's own
  cream fill it's actually drawn against — the exact "cannot know what is behind an element"
  limitation CLAUDE.md already documents as the reason `same_as_bg_scan` was retired from
  auto-running in `render()`. `invisible_craft_scan` has the identical structural blindness but
  is still live in `preflight`'s advisory bundle, quietly crying wolf on every bordered light
  object on a dark page. Never a hard fail (advisory), so it never blocked anything, but it is
  exactly the "noisy check trains people to skim past warnings" failure mode CLAUDE.md §7's own
  `preflight` docstring warns about for a DIFFERENT check (`under_filled_quadrants`).
- `preview.critique`'s `flat_dominant` and `sparse` flags on v6 — both correct measurements
  (the near-black ground genuinely covers >52%, fill genuinely is 0.24) but both describe the
  reference's OWN deliberate aesthetic (measured coverage 0.305, i.e. ~70% negative space) rather
  than a defect. There's no per-piece exemption available for a bespoke Workflow-B script the way
  `ARCHETYPE_PROFILES` gives Workflow A pieces like `giant_type` an exemption for an intentionally
  dominant dark field — worth a documented pattern for Workflow B ("if the reference itself scores
  flat/sparse on `compare.geometry`, expect and discount the matching `preview.critique` flags").

**Stayed silent on something real:** nothing in the automated stack caught the invisible-lightning
bug (section 1) — only the looking gate (Reading the PNG) found it. That is, in fairness, exactly
what CLAUDE.md §3 predicts ("the only reliable check is LOOKING") and the system worked as
designed: I looked, I found it, I fixed it, I'm reporting it for encoding. `dominance_check`
correctly stayed silent because I correctly didn't call it (its own docstring: "scatter collages
legitimately have no hero" — I read that and skipped `expect_hero`; a rare case of the doc
matching reality with no surprise at all, worth noting as a positive).

## 6. Where SCORE disagreed with EYE, with numbers

- **v3 (0.219) vs v4 (0.232):** v4 looked visibly MORE like the reference by eye — pills
  genuinely interleaved through the stickers, matching the reference's tangled-pile mechanism —
  yet scored worse. `compare.py`'s 9x11 region grid rewards matching the reference's SPECIFIC
  empty/full cells, which is not the same signal as "reads as an appropriately tangled pile."
- **v6 (0.169) vs v7 (0.189):** v7's `area_ratio` moved measurably closer to the reference's
  ideal (0.97 vs v6's 0.918, both technically inside the 0.75-1.3 non-blocking band) yet the total
  score got WORSE, because growing everything 1.27x vs 1.22x pushed the SAME three region cells
  further from the reference rather than closer. Neither disagreement is a metric bug — both are
  the metric correctly measuring exact positional/regional match, which is a narrower target than
  "looks right" — but they are real, reproducible cases where chasing the number would have moved
  the design further from a good composition, not closer.
- **v9 (0.241), the worst score of the run, also looked worst by eye** — this is the one case
  where score and eye agreed on the direction (both bad), which is worth stating for balance: the
  metric isn't ALWAYS misleading, it disagreed specifically in the "already close, fine-tuning"
  regime and agreed in the "clearly worse" regime.

## Top 3 friction points (for the summary)

1. The `.dood{z-index:4}` + wrapper-`transform` stacking-context bug — a real, silent,
   gate-invisible failure mode of a rule (§10's own `.dood` z-index convention) that nothing in
   CLAUDE.md documents, found only by looking at the rendered PNG.
2. `scatter_solve`'s single `max_pair_overlap` cannot serve a pile that mixes redundant-content
   objects (stickers) and single-shot-label objects (pills) — required inventing a two-call
   protect/keep_out decomposition the tool's docs don't suggest, and got there only after shipping
   a clipped word ("LINKED") in an intermediate version.
3. Two structurally blind advisory checks (`invisible_craft_scan`'s page-bg-only comparison,
   `collision_check`'s bounding-square treatment of circular objects) that fire identically and
   incorrectly on every render of this kind of piece — both are known INSTANCES of a limitation
   CLAUDE.md already names in a different context (same_as_bg_scan's retirement note), just not
   yet applied to these two.
