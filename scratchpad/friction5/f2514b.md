## 0. THE HEADLINE QUESTION: did the new protocol guidance actually help?

**Honest answer: this run cannot cleanly test that, because I was handed the diagnosis, not left
to find it.** My task brief quoted both defects (band-sorting vs. interleaving, and the
undersized high-contrast footer) verbatim, and `RECREATION_PROTOCOL.md`'s "WHEN THE REGION ROWS
ARE LYING TO YOU" section names this exact sample as its own worked example — I read that
section knowing in advance what it was going to tell me. So I did not independently discover the
arrangement defect; I confirmed it. Anyone asking "would the written protocol alone have caught
this for a fresh agent with no other briefing" has to look at how the ORIGINAL v6 was built, not
at this run — and the answer there is already known: v6's own builder had the three-question
framework unavailable (it was written *because of* v6's failure), reported "every element present
and correctly proportioned," and shipped the exact defect this session was sent to fix. That is
the real evidence the guidance was needed, not anything I did here.

What I *can* honestly report, because it happened live, in this session, without being told in
advance:

- **The underlying PRINCIPLE — "a paired over/under-filled region delta with balanced totals
  means wrong shape/position, not a missing element, so re-measure before adding filler" —
  transferred to a brand-new instance of the failure I was not told about.** v10's
  `REGION UNDER-filled row6-7/col3` and `row7/col7` were not part of my briefing; I diagnosed
  them myself as position error (not missing content) using exactly this logic, re-measured, and
  fixed one in v11. That is the protocol working as designed, on a fresh case.
- **It did NOT stop me from making a measurement mistake of the same species the protocol
  warns about, twice, within this session.** Both my first (5%-grid) and second (2%-grid) reads
  placed the "heart" sticker's centre at x≈0.85-0.88; the true position (found only on a third,
  1%-grid pass with axis labels burned into the crop itself) is x≈0.74. The protocol tells you to
  re-measure when the region deltas look wrong; it does not tell you your *measurement technique*
  can be wrong in a way no gate catches (see item 2 below) — I had to independently notice the
  gridline labels had been silently cropped away in my second attempt before I trusted a third,
  more careful pass. This is a real limitation of "just measure more carefully" as a written
  instruction: it does not specify HOW to measure so that a mistake in the measuring is
  self-evident, and I do not think a fresh agent following the protocol's prose alone would have
  been guaranteed to catch this without independently reasoning about it, which is exactly the
  "Opus-grade visual judgment" the protocol says it wants to avoid depending on.

**Verdict, stated plainly since the brief asked for one:** the guidance is real and it generalizes
(item 1 above is genuine evidence), but "read the guidance, then look" is not yet a fully
mechanical, judgment-free loop the way the rest of `RECREATION_PROTOCOL.md` aspires to be — the
re-measurement step it prescribes has its own silent failure mode (item 2 below) that the
protocol does not name.

## 2. APIs that surprised me

1. **`resolve_label_z` can silently re-bury a label that was previously fine, and its
   `unresolved` return value will not tell you.** Concrete repro, with the actual debug numbers:
   z-seed was `{hand:10, linkedin:11, instagram:12, dribbble:13, behance:14, facebook:15,
   heart:18, tongue:20}`. `instagram` and `behance` genuinely overlap (the reference tucks
   BEHANCE under INSTAGRAM's tail), and at the seeded z (behance=14 > instagram=12) the render
   showed "INSTAGRAM" clipped to "INSTAGR" — a real, visible miss. The function's own report that
   run was `resolve_label_z: UNRESOLVED: ['dribbble']` — **not** `instagram`, the label that was
   actually visibly broken on screen. Re-ordering the seed so `behance` sits BEHIND both its
   neighbours (`behance:12 < instagram:13 < dribbble:14`) fixed the seed conflict, but the
   function then raised `behance` on its own initiative to **z=21** (`DEBUG new_z:
   {..., 'behance': 21, ...}`, ABOVE even `tongue` at z=20, the piece's own explicitly-intended
   frontmost object) to satisfy behance's OWN visibility — which necessarily re-buries whatever
   THAT now covers. The root cause, confirmed by reading `layout.py:934-994`: each pass picks the
   single worst-covered object and raises it to `max(z of whatever currently covers it) + 1`, with
   no concept of "this seed order was chosen on purpose" or "don't re-break something that just
   got fixed." It converges (no infinite loop, no crash) but it converges to *a* solution, not
   necessarily one that respects the caller's intended front-to-back story. The actual fix needed
   THREE separate levers together — reordering the z-seed, shrinking the protected "label box" for
   pills to the inner ~80% instead of the whole rounded capsule so an end-cap graze doesn't count
   as equal to clipping a word, AND a ~2% manual position nudge to reduce the raw geometric overlap
   — z-order changes alone were not sufficient even after both of the first two fixes were in
   place; only adding the position change stopped the z=21 bump from recurring.
2. **`resolve_label_z`'s `min_visible` is an AREA fraction, not a per-character guarantee, and a
   label's readability is not evenly distributed across its area.** "INSTAGRAM" clipped to
   "INSTAGR" is a loss of 2 of 9 characters (~22%) concentrated entirely at the RIGHT end of a
   wide, mostly-empty-padding rectangle — well within what an 80%-area-visible threshold would
   accept as "resolved" if the covered region happens to land where the padding is thin and the
   letters are dense. This is a structural mismatch between what the check measures (box area)
   and what actually matters (are any specific glyphs fully gone) that nothing in CLAUDE.md's
   description of the function mentions. It is the direct cause of item 1 not showing up as
   `unresolved` even though it was visibly broken.
3. **`reconcile.measure_dom`'s advisory `UNTRACKED span` line fired on the LINKEDIN pill
   specifically, every single render (v10-v14), never on any other pile object.** Reported as
   `UNTRACKED span at (182,430) 164x76` — those numbers are exactly LINKEDIN's UNROTATED CSS box
   (center-derived: `w=164` matches its computed pill width, `h=76` matches `PILL_H`, and the
   top-left `(182,430)` is precisely `center - (w/2, h/2)` for its placed centre). My declared
   `elements` entry for every pile object is the ROTATED bounding box (via `lay.rotated_bbox`,
   per §6's own template and §10's own bug-catalog row about stale bboxes) — so this reads as
   `reconcile_boxes` finding the div's own pre-transform layout box as a SEPARATE, undeclared span
   in the DOM, distinct from the rotated box I told the gate about. It never blocked anything
   (advisory only) and I did not chase it further given the iteration budget, but it is the SAME
   neighbourhood of issue the prior friction doc left as an open, undiagnosed question (`BBOX
   UNDER-REPORTS tongue_illustration: declared 89.08x89.08, drawn 204x62`) — two different rotated
   elements, two different DOM-reconciliation surprises, in two different sessions, on the same
   poster. That is enough of a pattern to say rotated-element reconciliation is a soft spot, not a
   one-off, even though I can't fully diagnose the mechanism from either occurrence alone.
4. **`text_pairs` was never populated by either session (v1-v9 or v10-v14), so
   `layout.text_contrast_check` — documented in CLAUDE.md §7a as running a "HARD FAIL" check —
   never actually ran on this poster once, across 14 iterations.** It is correctly opt-in (§6's
   template says so explicitly), but nothing prompts an author to reconsider that when a piece
   has FIVE separate text-on-surface decisions (wordmark on ink, five pill labels on cream, one
   footer line on ink at reduced opacity) and zero of them were ever checked. My footer's
   opacity-based "wash" effect is exactly the kind of choice this check would be relevant to (see
   item 5) and it was silently never exercised.

## 3. Gates that fired on nothing, and the one real blind spot I introduced on purpose

**Fired on (essentially) nothing, every render, same as the prior session's report:**
- `IGNORE PAIRS NAME NO data-tag IN THE DOM` — identical cosmetic noise, same root cause
  (`collision_ignore` forwarded to both `layout.collision_check`, which matches labels, and
  `audit.audit`, which matches `data-tag`; bespoke scripts set neither). Fired on every one of
  v10-v14's renders.
- `invisible_craft (advisory): [('border', '#0A0A0A', '#0a0a0a', 0.0)]` — identical to the prior
  session's report, same structural cause (compares a bordered element's outline to the PAGE
  ground rather than its own local backing surface). Fired on all 10 renders this session
  (preflight ran twice per script — once standalone, once inside `render()` — so it prints twice
  per version).

**A blind spot I introduced deliberately, and flagged in the script's own comments rather than
letting it pass silently:** the footer's low-contrast "wash" effect is CSS `opacity:0.4` on the
literal `CREAM` token, not a different, actually-dimmer colour. `text_contrast_check` (had it been
wired in — see item 2.4) would evaluate the DECLARED colour pair (`CREAM` vs `INK`, ~17:1, passes
by a wide margin) and has no way to see the runtime `opacity` that makes the rendered pixels
actually read as a dim gray (~rgb(98) measured against the reference's own footer, which is doing
the same kind of thing). This is not a bug in the check — a hard hex-on-hex contrast check has no
principled way to also model arbitrary alpha compositing — but it means "this text is DELIBERATELY
low-contrast as a design choice" and "this text is ACCIDENTALLY low-contrast and illegible" are
indistinguishable to every static check in the stack, and only the looking gate can tell them
apart. Recorded here per CLAUDE.md §8's spirit (name the class of gap even when not fixing the
engine).

## Top 3 friction points (for the summary)

1. **`resolve_label_z` can silently re-bury a previously-fine label as a side effect of fixing a
   different one, and its `unresolved` return value names only the LAST failure in its own
   internal pass order — not necessarily the one that is visibly broken on screen.** Confirmed
   with exact z-values (behance seeded at 14, bumped to 21 — above the piece's own intended
   frontmost object — while `instagram` silently went from readable to clipped without ever
   appearing in `unresolved`). Root cause is architectural (each pass optimizes the single
   worst-covered object with no memory of the caller's intended ordering) and its `min_visible`
   threshold is area-based while text readability is not evenly distributed across a label's area,
   so a technically-80%-visible box can still be missing whole characters at one end.
2. **The measurement methodology the protocol prescribes ("measure carefully, re-measure when
   region deltas look wrong") has its own silent failure mode that nothing in CLAUDE.md or
   RECREATION_PROTOCOL.md names**: a hand-drawn coordinate grid can lose its own axis labels to a
   later crop, producing a confidently wrong number that looks exactly like a correctly-measured
   one. This cost two full mismeasurement-and-rebuild cycles (v10, v11) before a third pass, drawn
   with labels burned into the already-cropped image, found the real position of the "heart"
   sticker was off by 0.14 of the canvas width from BOTH earlier reads.
3. **This session cannot honestly claim the new protocol guidance would have caught v6's
   arrangement defect for a blind agent**, because the task brief stated the diagnosis outright
   and the protocol section in question was written using this exact sample as its worked example.
   What I can honestly report is narrower and still real: the underlying principle (a paired
   region over/under-fill with balanced totals means wrong shape/position, re-measure before
   adding filler) transferred correctly to a brand-new instance of the same failure class that
   nobody told me about in advance (v10's col3/row6-7 gap), which is genuine evidence the
   guidance generalizes — just not proof that written guidance alone replaces looking.
