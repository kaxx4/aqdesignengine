## 2. The reference is a STORY poster (0.5625:1); the abandoned attempt built it on FEED (0.8:1). This is a bigger deal than an aspect mismatch footnote — it explains the entire miss.

`Image.open(ref).size` = `(1200, 2133)` = 0.5625:1, which is `core.SIZES['story']` (1080x1920)
to four significant figures. `orbit_stickers()` used `core.SIZES["feed"]`. CLAUDE.md §5 step 0
says "measure the reference first" and lists `compare.geometry` but doesn't explicitly say
**"check core.SIZES for the reference's own aspect before building anything"** — geometry()
reports fractions, which are aspect-agnostic, so nothing in step 0 forces you to open the JPG
and check its raw pixel dimensions against `core.SIZES`. I only caught this by running
`Image.open(ref).size` on a hunch after the aspect-mismatch warning printed on the orphaned
PNGs. **Suggested addition to §5 step 0: compare the reference's raw W/H to `core.SIZES`
explicitly, before geometry() fractions are even computed** — a 30%+ aspect gap silently
degrades every fraction-based measurement compare.py produces, and the warning is currently
only surfaced as a side-effect of calling `compare.compare()`, not `compare.geometry()`.

## 3. `shapes.sticker()`'s forced-square viewBox makes wide/elongated silhouettes look wrong, and there's no documented recipe for fixing it

`capsule(w, h)` returns a path in a `0..w` x `0..h` box, but `sticker(path, fill, size=X,
box=100)` always draws a **square** `box x box` viewBox. For `capsule(w=100, h=40)` (the
existing convention used elsewhere in the corpus, e.g. `gen_showcase5h.py`'s badge props),
the pill only occupies the top 40% of the square viewBox, leaving 60% of the declared bbox
empty/transparent. For a small accent badge this is invisible; for a HERO-scale elongated
character (my "bunnyStretch" element, meant to echo the reference's stretched-out bunny
sticker) it produces a visibly lopsided result — the shape reads as sitting in the upper
portion of its box with a dead gap below. I worked around it by using `h=70` (closer to
square) and relying on a large negative rotation to disguise the gap, which is a hack, not a
documented pattern. **shapes.py has no `sticker_wide()` / no way to pass a non-square
viewBox**, and nothing in CLAUDE.md §9's sticker section flags this as a known limitation —
it's implied by careful reading of `sticker()`'s own docstring ("THE RENDERED BOX IS ALWAYS
size x size, SQUARE") but that docstring is about the DECLARED BBOX being square, not about
the visual consequence of drawing a non-square path inside a square viewBox with padding.

## 4. `bleed_tags` has TWO enforcement paths that disagree, and only one of them is documented as needing `data-tag`

This is the same class of bug the manual's own bug catalog documents for `collision_ignore`
("audit.audit(ignore_pairs=) matches the DOM's data-tag while layout.collision_check matches
the caller's element LABELS"), but `bleed_tags` has the identical split and it is **not**
called out anywhere in §7 or §10:

- `render(..., bleed_tags=("starRedBig",))` forwards `bleed_tags` to BOTH
  `layout.preflight` (which runs the STATIC `bounds_check` on the python-side tuple list) and,
  via `_shoot`, to `reconcile.measure_dom` (which matches on the DOM's `data-tag` attribute,
  confirmed by reading `engine/reconcile.py` line 376: `if e["tag"] in bleed_tags`).
- Passing the element's own LABEL as the bleed tag (`bleed_tags=("starRedBig",)`, mirroring
  how `collision_ignore` labels work) does **nothing** for `measure_dom` — it silently matches
  zero DOM elements because no div in my HTML carried `data-tag="starRedBig"`. I only found
  this by grepping `engine/reconcile.py` for `bleed_tags`; nothing in CLAUDE.md's §6 template
  or §7a bullet list says bleed_tags needs an HTML `data-tag` attribute, and the template's own
  comment (`bleed_tags = () # e.g. ("pill",) for a field that runs off both edges`) reads as a
  CATEGORY name, not a warning that you must also emit `data-tag="pill"` in your markup.
- **Worse: even after adding `data-tag="bleed"` and `bleed_tags=("bleed",)`, the STATIC
  `layout.bounds_check` inside `preflight` STILL reports the element as `off_canvas`.**
  `bounds_check` operates purely on the python-side `(label,x,y,w,h)` tuple list and, per a
  read of `engine/layout.py`, does not appear to accept or honour a bleed exemption at all —
  only the DOM-based `measure_dom` does. So a genuinely-declared, correctly-tagged intentional
  bleed element will ALWAYS show up in `preflight`'s `ISSUES: off_canvas` print, forever,
  because two different gates in the same call disagree about whether "declared as bleed"
  means anything. Exact repro: with `elements=[("starRedBig",-54,720,216,216), ...]` and
  `bleed_tags=("bleed",)` + `data-tag="bleed"` on that div, `render()`'s printed output was:
  ```
  [preflight] ISSUES:
     - off_canvas: [(9, -54.0, 720.0, 216.0, 216.0)]
  ```
  while the SAME render's `measure_dom` pass printed no OFF-CANVAS line for that element at
  all (it correctly recognised the bleed). This means **a piece whose mechanism is a
  legitimate edge bleed can never make `preflight`'s ISSUES list empty**, which is exactly the
  "teaches you to read past a failing verdict" failure mode CLAUDE.md's bug catalog already
  names for a DIFFERENT bleed gap (§10, "session 10f, agent g1") — this is a second, still-open
  instance of the same class, in the static/DOM split rather than the render()-forwarding gap
  that session fixed.

## 5. `invisible_color_check` (PAPER/CREAM) fires exactly as documented, but there's no way to mark "accepted, craft layer carries it" so it stops appearing every run

Two elements (`bunnyStretch`, `birdCream`) use an off-white (`#FAF6EC`) on the cream page
background (`#F4EFE0`) — distance 15.1, close enough to trip `invisible_color_check`. §9
explicitly documents this exact pair class ("PAPER and CREAM are 1.15:1 apart... Give the
card its craft layer, or change one of them") and `sticker()`'s outline+shadow treatment IS
the craft layer that's supposed to make this acceptable — confirmed by eye, both stickers are
clearly visible via their black outline. But `color_pairs` (the mechanism for declaring this
to the checker) has **no way to say "yes, I know, the outline carries it"** — the check has no
accept-and-suppress path, so it reprints on every single render regardless of whether the
outline is present, which is a real "cries wolf" pattern per the manual's own stated design
philosophy ("A gate that cries wolf on every clean run is how people learn to skim past the
warnings that matter" — used to justify OTHER design decisions in §7, but not applied to this
specific, pre-documented, always-going-to-recur case).

## 6. `S.sticker()`'s baked-in rotation makes the DECLARED bbox wrong by design, and there's no helper to fix it even though `layout.rotated_bbox` exists for exactly this

`bunnyStretch` is `capsule(w=100,h=70)` at `rot=-24` inside `sticker(..., size=367.2)`. Actual
rendered footprint per `reconcile.measure_dom`: 426x426, a 16% over-run vs the declared
367.2x367.2 square — this is precisely the case `layout.rotated_bbox(x,y,w,h,deg)` exists to
solve (§7a, §10: "Rotated element's real footprint is bigger than its CSS size — a 168px
sticker at -9° draws 192px"). But nothing in the §6 template or the `stick()` pattern actually
CALLS `rotated_bbox` when appending to `elements` — you have to know to do it, compute it by
hand, and there's no single combinator like `stick_declared(shape, fill, x, y, size, rot)` that
returns both the HTML and the correctly-expanded bbox tuple in one call. I left this as an
advisory `BBOX UNDER-REPORTS` warning rather than fixing it, since it's non-blocking and
purely cosmetic to the gate's own bookkeeping — but it's exactly the kind of paper-cut the
manual says it wants eliminated by encoding (§1, §8).
