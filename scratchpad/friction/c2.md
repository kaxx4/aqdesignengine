# Friction log — c2 (Workflow C, story canvas)

Task: `python design.py "monsoon reading camp - sign-ups open" --dept events --canvas story --seed 41`,
then a bespoke build from `core`/`build`/`layout`/`shapes`/`doodles` (never `engine.py`'s ARCHETYPES),
at 1080x1920 (story), not the default 1080x1350 feed.

Scripts: `scratchpad/c2_v1.py` .. `c2_v5.py`. Final render: `out/session10f/c2_v5.png` (v5).
Reference used by the drawn style: `training_samples/reference_posters/2022ebef4ffad554b42b3d6c5c6c914a.jpg`
(2022ebef4ffad5 — the "envelope + cascading identical cards" mechanism).

## Top 3 friction points (see detail below)

1. **Double rotation.** Both `doodles.stamp(rot=..)` and `shapes.sticker(rot=..)` already bake the
   rotation into the returned SVG's own inline style. Wrapping either in the CLAUDE.md-template
   style of "positioned div with `transform:rotate()`" (which is *exactly* the pattern the manual's
   §6 `doodle()` helper teaches for plain doodles, and which I extended to also rotate the wrapper
   for consistency with my other elements) silently doubles the visual tilt and desyncs
   `layout.rotated_bbox()`'s math from the true rendered footprint. Nothing errors; `reconcile.py`
   just reports a confusing `OVERSIZE ... under-reports by Npx` a few pixels off from what
   `rotated_bbox` predicts for the angle you *think* you're applying. This cost a full debugging
   pass (v2→v3) before I traced it to two independent rotation sources.

2. **A brand-new, undocumented, unconditional check with at least one demonstrated false positive.**
   `reconcile.measure_dom` now also runs a "BURIED TEXT" hit-test (`reconcile.py` lines 193-215),
   added per its own comment "session 10f, agent c1's v1" — i.e. added to the engine *during this
   very session*, by a sibling agent, and CLAUDE.md's §7b description of `measure_dom` (which only
   documents `clipped`/`spilling`/`off_canvas`/`boxes`) has not been updated to mention it at all.
   It fired on my render for `"WELCOME TO THE"` and `"OPEN"` — both texts are plainly visible in the
   actual PNG (confirmed by reading the rendered image, the only authority CLAUDE.md §3 recognizes).
   Unlike `collision_check`, it has **no ignore-list / opt-out parameter** — `preflight()` doesn't
   even see it, since it lives entirely inside `reconcile.measure_dom`, which `build.render()` calls
   unconditionally. There is no way to mark "this text is on a repeated cascade card and its
   duplicate is legitimately covered by the front card" the way `collision_ignore` lets you mark a
   by-design overlap. See full repro below.

3. **The manual's own canvas-size assumption leaks into module-level constants that don't matter for
   the render path, but DO matter for anyone reading the code to understand the gate stack**, plus
   one real behavioral trap: `build.render()`'s convenience wrapper (`elements=`/`color_pairs=`/
   `page_bg=`/`expect_hero=`) does **not** accept `cascade_stacks`, so a script using the deck/
   cascade mechanism (which CLAUDE.md's own bug catalog names as a first-class pattern,
   `cascade_peek_check`) cannot get cascade checking AND the "render also runs preflight for free"
   convenience from one call — you must call `layout.preflight()` yourself (with `cascade_stacks`)
   AND separately pass `elements=` to `render()` (for the `reconcile.suppress_handled` benefit), or
   you silently lose one of the two. I lost the second one for two full versions (v1-v3) without any
   error telling me so — `render()` just doesn't complain about a kwarg you didn't pass.

## Canvas-size (story vs. feed) findings — the specific thing I was asked to watch for

- **`design.py`'s brief and `compare.geometry()` are canvas-agnostic** (everything is reported as
  a fraction 0..1 of the image), so no problem there. The one lucky/unlucky wrinkle: the reference
  jpg for this style (2022ebef4ffad554b42b3d6c5c6c914a.jpg) is **736x1308px, aspect 0.5626** —
  effectively identical to story's own 1080/1920 = 0.5625. I only noticed this by actually checking
  the file's pixel dimensions (`PIL.Image.open(...).size`); nothing in `design.py`'s brief or
  `compare.geometry()`'s output states the reference's own aspect ratio, so a builder who doesn't
  think to check could easily reuse another script's feed-shaped adaptation (e.g.
  `scratchpad/gen_2022ebef4ffad5_v5.py`, which targeted 1080x1350) and get proportions that are
  wrong for story even though the *mechanism* transfers fine. **Ask:** `compare.geometry()` could
  cheaply report the source image's own W/H/aspect alongside the fractional numbers — it already
  opens the file.
- **Real hardcoded-1350 findings, graded by whether they actually bite:**
  - `engine/audit.py` — **already fixed**, with a `canvas=(W,H)` parameter and an explicit comment
    ("a story (1080x1920) audited against 1350 reported phantom bottom breaches"). `build.render()`
    passes `canvas=(W,H)` correctly. No live bug. Good example of an entry that WAS updated for
    story; I'm calling it out only so the ones below can be judged against it.
  - `engine/reconcile.py` line 18: `W,H=1080,1350` **and** lines 321-322 inside `probe()`:
    `if e['right']>1080-20 ... if e['bottom']>1350-20` — genuinely hardcoded, not parameterized.
    Harmless for me because `probe()` is the legacy Workflow-A-only driver (module's own docstring:
    "Prefer measure_dom") and my render path never calls it — but if anyone reaches for `probe()`
    on a story piece expecting the same behavior as `measure_dom`, this silently reports phantom
    bottom/right breaches at the WRONG edge (1350 instead of 1920, 1080 is at least right for width).
  - `engine/layout.py` line 70, `bounds_check`'s docstring: *"Canvas is 1080x1350 for feed (NOT
    ~1700+)"* — the function itself takes `W,H` as real parameters and is fully story-safe; this is
    pure documentation staleness, but it reads exactly like an assertion of a hard constraint, and I
    double-checked the function body before trusting it because of that wording.
  - `engine/reconcile.py` line 426 default: `def wash_scan(html, W=1080, H=1350, ...)` — only matters
    if a caller omits the args; `preflight()` always passes real W/H through, so not live for me, but
    worth knowing the default itself is feed-shaped.
  - `engine/compare.py` line 33: `SIZE = (540, 675)` "common analysis resolution (feed aspect 4:5)",
    with its own comment admitting the assumption and a separate note at line 239 that the whole
    scoring pipeline was built around "a single 1080x1350 poster." I didn't run `compare.py`'s
    scoring functions against my story render (Workflow C has no reference to score against), so I
    can't say whether this actually distorts anything for a story canvas — flagging it because
    CLAUDE.md doesn't mention this caveat anywhere and a future recreation done at story size would
    hit it immediately.
  - **Net finding:** nothing in the render path I actually used (`build.render`, `reconcile.
    measure_dom`, `layout.preflight`, `audit.audit`) mis-measured anything because of the story
    canvas — the parameterized versions are used correctly and consistently. The risk is entirely in
    the *legacy/secondary* tools (`reconcile.probe`, `compare.py`'s scoring) and in documentation
    (`layout.py`'s docstring) that still speaks as if 1080x1350 were the only shape, which could
    mislead the next person even though it didn't mislead the actual gate.

## API surprises, in the order I hit them

### 1. `shapes.sticker()` always renders a SQUARE `size x size` canvas
The function signature takes one `size` for both width and height regardless of the silhouette's
own proportions. I declared a wide, short cloud silhouette (`CLOUD_D`) with a non-square bbox
(220x150) in my `elements` list to match how it *looked* conceptually — the actual rendered `<svg>`
is always `size x size`, so `reconcile.measure_dom` correctly reported the true (square) render as
`OVERSIZE ... real height 224px vs 150px box`. Nothing in `shapes.py`'s docstring says "this is
always square" — you have to infer it from `return f'<svg ... width="{size}" height="{size}" ...'`.
Fix: declare every sticker's box as `size x size`, full stop, no matter what the silhouette looks
like inside that square.

### 2. Double rotation (detailed)
`doodles.stamp(kind, color, rot=..)` passes `rot` straight into the underlying doodle function,
which bakes `transform:rotate({rot}deg)` into the `<svg>` tag's own `style`. `shapes.sticker(...,
rot=..)` does the identical thing on its own `<svg>`. CLAUDE.md §6's template `doodle()` helper
wraps `dd.stamp(fill=fill, rot=rot)` in a plain absolutely-positioned `<div>` **without** rotating
that div — so the template itself is safe. My mistake was generalizing my own `at()` helper (which
DOES rotate its wrapper, for the plain rectangular elements like cards) to doodles/stickers too,
passing `rot` to both the wrapper's `transform` AND into `stamp()`/`sticker()`. Every rotated
doodle/sticker in v1-v2 rendered at 2x its intended angle, and `layout.rotated_bbox(x,y,w,h,rot)`
— computed for the single angle I thought I was applying — under-reported the true footprint by a
consistent, confusing amount (visible in the collision-check numbers, e.g. a "90.36" bbox for a
78px star at "10°" that only makes sense once you realize the true angle drawn was 20°). This isn't
called out anywhere as a trap; a script that uses one rotation source consistently (either only the
wrapper, or only `stamp`/`sticker`'s own `rot`) never discovers it.

### 3. `box-sizing:border-box` eats declared content width — same bug, new location
CLAUDE.md's bug catalog already has this row ("every pill in a 28-pill field clipped by 5-6px" —
motifs v3). I still hit a fresh instance: my `card()` div is `box-sizing:border-box` with a 5px
border, so its content box is `w-10` wide/tall, not `w`. I gave the interior hatch-pattern overlay
an explicit `width={w}` (the full outer width, not the border-box interior), and `reconcile.
measure_dom` reported `CLIPPED div: width 620px inside a 610px box` — exactly 10px, exactly
`2*border`, on all three cascade card scales. The catalog entry's own fix ("add `2*border` when
sizing a box to its measured content") is correct and I applied it, but it's easy to reintroduce
because it's not the OUTER card box that's wrong (that one I sized correctly), it's a decorative
CHILD inside it — the bug recurs per-child, not per-component.

### 4. `build.measure_text`'s "flow off `h`, size collision boxes off `ink_h`" guidance is
   backwards for an absolutely-positioned layout
The docstring is correct for normal CSS document flow (where the browser actually reserves `h` for
the next sibling). Every AQ bespoke script positions everything with `position:absolute` and
hand-typed `top:`, though — there IS no next-sibling auto-flow, I am the one deciding where the next
element starts. Flowing my headline's second line off `h` (as the docstring's own example suggests)
put it 24px into the first line's real painted extent, because at `line-height:0.86` the div's
`ink_h` (168px, confirmed by instrumenting the render — see below) is meaningfully taller than its
layout `h` (136px). For a script that positions everything by hand, the safe rule is the opposite of
what's written: **flow off `ink_h`**, and reserve `h` only means something when you are relying on
the browser's own block flow to place the next element for you.

### 5. `build.render()`'s convenience preflight has no `cascade_stacks` parameter
`layout.preflight()` accepts `cascade_stacks` for `cascade_peek_check`; `build.render(html, out, W,
H, elements=, color_pairs=, page_bg=, expect_hero=, collision_ignore=, auto_nudge=)` — no
`cascade_stacks`. So a script using the cascade/deck pattern (exactly what CLAUDE.md's bug catalog
names `cascade_peek_check` for) cannot rely on `render()`'s auto-preflight alone; it must call
`layout.preflight()` itself first (to get the cascade check), and I assumed that made passing
`elements=` to `render()` **redundant** — so I called `render(html, out, W, H)` with no kwargs at
all in v1-v3. That silently drops `reconcile.suppress_handled(flaws, elements)` (only runs `if
elements:`), so every headline `spilling`/OVERSIZE warning printed even for boxes I had correctly
sized off `ink_h`. Nothing errors or warns that you've done this; the gate just gets quietly noisier
than it should be. Fixed by passing `elements=`/`color_pairs=`/`page_bg=`/`expect_hero=`/
`collision_ignore=` to BOTH the manual `preflight()` call and to `render()` — which means
`preflight()` genuinely runs twice per render (once manually, once inside `render()`), printing two
near-identical `[preflight] ...` blocks. Harmless, but a script has to choose between "clean single
gate report" and "get cascade checking + suppression" — it can't have both from one call.

### 6. The new BURIED-text check, and why it's a false positive here (full repro)
`reconcile.measure_dom`'s hit-test samples 5 points of an element's **own bounding rect**
(`[.5,.5],[.2,.3],[.8,.3],[.2,.7],[.8,.7]`) and calls `document.elementFromPoint` at each; if ALL 5
land on some other element (not `e` and not contained by `e`), it's reported buried. For a
full-width, `text-align:center` container (exactly the pattern `build.py`'s own `eyebrow()`/`cta()`
helpers use, and the pattern I used for "WELCOME TO THE" — `left:0;right:0;text-align:center`), the
box's own bounding rect is `x:0..1080`, but the actual glyphs occupy only the centered ~600px. The
`.2`/`.8` fraction points land on **empty space within the div's own box** — and CSS still resolves
`elementFromPoint` there to whatever is UNDERNEATH at that pixel (a transparent div's empty area is
not itself hit-tested preferentially over a differently-stacked sibling occupying the same screen
pixel — I could not fully pin down why even the CENTER `.5,.5` point also missed for these two
specific elements, since visually nothing legitimate covers them; my working theory is the grain
overlay `.p::after`, `pointer-events:none`, or a stacking-context interaction with the `.p` root, but
I did not chase this to ground given the "report don't patch" constraint). I confirmed it's a false
positive the only way CLAUDE.md trusts: reading the actual PNG — "WELCOME TO THE" and "OPEN" are
both plainly visible in `out/session10f/c2_v4.png` and `c2_v5.png`. **There is no
`collision_ignore`-style opt-out for this check.** Worth noting for whoever owns this: the "OPEN"
instance is *separately* explainable as a likely-legitimate case even if the check worked correctly
— it's the back cards' duplicate "OPEN" text, genuinely covered by the frontmost identical card,
which is the intended cascade effect (same duplicated content on all 3 cards, per the recipe) — but
the "WELCOME TO THE" instance has no such excuse and looks like a real check bug, not a real
composition bug.

## Iteration log (what each version actually cost)

- **v1** (~first full pass): built the whole composition — header, measure_text-sized headline,
  cascade deck, custom book/umbrella/cloud silhouettes (no such doodles exist in `doodles.py`),
  envelope, footer — in one shot, then ran the gate. Got back 19 collisions, 3 false "invisible
  color" reports (my own mistake — I checked the base ground fill against itself), and 6 reconcile
  CLIPPED/OVERSIZE lines. This is normal/expected for a from-scratch bespoke layout; the value of the
  gate stack was real here — it caught a genuinely invisible envelope panel (SKY-on-SKY) I would not
  have noticed by eye until much later.
- **v2**: fixed the invisible-color setup mistake, squared the sticker boxes, fixed the headline
  flow direction. Down to 9 collisions, 1 bad invisible-color pair, 3 CLIPPED, 3 OVERSIZE. The
  OVERSIZE set didn't fully go away here — that's the double-rotation bug, not yet diagnosed.
- **v3**: found and fixed double rotation (traced by computing `rotated_bbox` by hand and comparing
  to what the collision numbers implied about the actual angle). CLIPPED/invisible-colors gone. Down
  to 7 collisions + 1 unexplained `OVERSIZE div: real height 169px vs 136px box` with a bare `div`
  tag and no other identifying info. Chasing that one line took a genuine side-investigation: copied
  the script, hooked `reconcile.measure_dom` directly against the live page to dump every box in the
  136-180px height range, matched `(x=0,y=168,w=1080,h≈169)` to the headline's `y_mon=168`, then
  printed `measure_text`'s raw `h`/`ink_h` values to confirm `mon_h=136` exactly. That's when I found
  finding #5 above (render() never saw `elements=`, so `suppress_handled` never ran) — the box was
  never actually wrong, the gate just wasn't told to trust it.
- **v4**: repositioned the remaining genuine collisions (a star sitting inside the header's safety
  bbox, a leaf fully inside the tree's bbox, cloud/raindrops slightly overlapping each other by
  design) instead of blanket-adding them to the ignore list, added `elements=` to the `render()`
  call. Reached `clean = True` other than the BURIED false positives (finding #2/#6) and the
  legitimate-but-noisy UNTRACKED-box advisories (every text div that isn't in my `elements` list at
  all, e.g. "ages"/"tagline"/"handle" — I only tracked elements with real collision risk, which is
  what `reconcile_boxes` is designed to flag as advisory, not fail on).
- **v5**: this was the actual **looking-gate** pass (CLAUDE.md §3), done only after the gates were
  clean, per the manual's own sequencing rule. Reading the v4 PNG surfaced three real visual defects
  no gate had (or could have) caught: (a) each cascade card was ~70% dead white space — the
  `reading_row` illustration was crammed into a 34%-height strip at the bottom and was nearly
  illegible at 3-figures-per-card scale; (b) the custom umbrella silhouette's 10-point scalloped
  fringe read as a crown/gear, not an umbrella, once actually rendered at size; (c) the envelope had
  a large unused gap between the RSVP block and the geography tag line. Fixed by replacing the
  3-tiny-figures row with one large seated-reader+book+rain-streaks mark filling most of the card,
  simplifying the umbrella to a plain half-disc canopy, and adding a schedule chip
  ("EVERY SAT & SUN · JUL-AUG") to the envelope gap. This is the step the manual is explicit that no
  amount of green gates substitutes for, and it was correct to be explicit about it — every issue
  found here was real and none of it showed up as a metric or gate failure.

Total: 5 versions. Roughly the first 3 were pure gate-driven debugging (the double-rotation bug in
particular was a genuine, non-obvious root cause requiring cross-referencing three different pieces
of output — collision numbers, OVERSIZE numbers, and the actual rendered angle — before it clicked).
The last 2 were composition fixes once the gate was trustworthy, in the sequence CLAUDE.md prescribes.

## What I had to guess (nothing told me directly)

- **How to translate the reference's fractional geometry into story-canvas pixels when the two
  aspect ratios happen to coincide.** `design.py`'s brief and `compare.geometry()` give fractions,
  not the reference's own pixel size, so I had to separately open the file to notice the aspect
  match was even usable directly (see the "Canvas-size findings" section above).
- **Which overlaps are "by design" vs. real bugs**, since `collision_ignore` requires the author to
  already know the answer. I treated it as: an overlap the *reference itself* clearly has (cards
  overlapping each other, a sticker grazing the deck/envelope seam, text sitting on the envelope
  panel) is by-design; anything else gets moved, not ignored. This isn't stated anywhere as the
  rule, but it's the only reading of §5 step 4's "acceptable adaptation vs. real miss" distinction
  that seemed consistent with how `IGNORE` sets are used in the existing `scratchpad/gen_*_v*.py`
  scripts I read for reference (e.g. `gen_2022ebef4ffad5_v5.py`'s reliance on `cascade_stacks`
  rather than blanket card-card ignoring — though that script predates `collision_ignore` support in
  `preflight` and doesn't use it at all, so even that precedent is partial).
- **Book/umbrella/rain-cloud silhouettes**, since none exist in `doodles.py` or `shapes.SILHOUETTES`
  — built as raw inline SVG paths per the template's "inline the path inside art SVGs" rule, sized
  by trial (there's no `INNER_FRAC`-style guidance for a hand-rolled path the way there is for the
  named `shapes.py` silhouette families).
- **Whether flooding the page ground in the department accent (sky) for this style contradicts
  CLAUDE.md §9's "accents are punctuation only (~30%), never a flooded field."** The drawn style's
  own recorded recipe explicitly says "solid saturated ground," matching the reference exactly
  (coverage 0.50 measured). I treated this the same way `ARCHETYPE_PROFILES` treats `giant_type`'s
  dark base — an intentional per-style signature that overrides the general punctuation guidance —
  but nothing in `design.py`'s output or CLAUDE.md says Workflow C recipes are allowed to override
  §9 this way; I inferred it from the giant_type precedent. Worth a explicit ruling for whoever
  reads this next.

## What was genuinely fine (no drama, worth saying so plainly)

- `design.py "..." --dept events --canvas story --seed 41` worked exactly as documented, first try,
  printed a usable brief with a real measured recipe and the correct department color/contrast
  values.
- `compare.geometry()` ran cleanly against the reference and gave numbers I could act on directly.
- `core.accent_for`, `core.ink_of`, `core.on_cream`, `core.text_on` all behaved exactly as
  documented — no surprises, no drift from the measured-contrast promise in §9.
- `B.measure_text` itself (once I understood the `h` vs `ink_h` flow direction correctly) gave
  exact, trustworthy numbers every time — the two-phase "measure at size=100, scale linearly, then
  measure again at the real size" approach worked cleanly with no iteration needed.
- `layout.rotated_bbox`, once the double-rotation confound was removed, matched the rendered
  footprint exactly.
- `PYTHONIOENCODING=utf-8` was in fact necessary — omitting it was not tested here since the
  instruction was followed from the start, but the checkmark glyphs in gate output (✓/⚠) are real
  and would have broken on Windows' default codepage.

## Final verdict

**v5**, `out/session10f/c2_v5.png`. All hard gates clean (`preflight` clean, `audit` margins/overlap
clean, no CLIPPED, no genuine OVERSIZE, no invisible colors). Remaining printed warnings are the two
BURIED false positives (finding #2/#6, confirmed against the actual pixels) and UNTRACKED advisories
for text elements I deliberately didn't add to the collision-relevant `elements` list.

Looking-gate verdict: **genuinely happy with this one.** Clear single hero (the headline + cascade),
legible hierarchy, on-brand department color used correctly and consistently, a coherent
monsoon/reading motif carried through the cards, envelope, and ring of stickers (book, umbrella,
raincloud+drops, tree, leaf, star) instead of the reference's unrelated stock props, real CTA copy
(no fabricated stats/QR/stock imagery), and no dead card interiors or illegible type. The one
residual weakness I'd flag if pushed for a 6th iteration: the right-hand margin between the rain-drop
cluster (~y700) and the umbrella (~y1450) is thinner on content than the left column (book/tree/
star) — a minor balance asymmetry, not a defect, and not worth another full render cycle against the
gains already banked.
