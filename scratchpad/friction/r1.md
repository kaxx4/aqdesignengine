## APIs that surprised me

- **`layout.collision_check` has no concept of intentional containment.** Any element drawn
  *inside* its own parent card (a photo, a title, a body paragraph, a "Read" link sitting on a
  white card `div`) is reported as a collision against that card's own background — because the
  check is pure bbox-overlap over every pair, full stop. For a card-based layout (this reference,
  and presumably any future UI-mockup recreation) that means EVERY child needs to be hand-listed
  in `collision_ignore` against its parent, or the printed issues list fills with what look like
  bugs but are just "the text is inside the box it's supposed to be inside." On this piece that
  was 16 pairs by the final version. Miss one and it's indistinguishable in the output from a real
  collision — nothing in the printed tuple says "this looks like containment." A
  `contains`-style relationship (declare "this list of children belongs to that card") would
  remove an entire class of manual bookkeeping and a matching class of look-alike false alarms.

- **`engine/audit.py`'s margin check is hardcoded to `M=64`, independently of whatever margin the
  calling script actually uses.** (`engine/audit.py` line 3: `M=64` at module scope, used at line
  40's `bx['x']<M-3`.) I built this piece with `M=48` on purpose — a tighter margin appropriate
  to a mobile-app-UI reference whose own cards sit almost edge-to-edge — and every text element
  printed `MARGIN ... breaches safe area` even though nothing was actually broken. The fix was to
  switch to `M=64` purely to match audit.py's assumption, not because the design needed it. A
  bespoke script's own margin choice (which CLAUDE.md §6 explicitly says is discretionary — "the
  template said 48 and nothing else did") has no way to inform this check.

- **`B.measure_text()` with `max_width` set returns the WHOLE wrapped block's height in `h` /
  `ink_h`, not a per-line height.** This is stated correctly in the docstring, but I still got it
  wrong on the first pass (assumed a returned 60px was "one line of a two-line block" and
  multiplied it by 2 for a body paragraph), which silently doubled the reserved height for every
  body-copy block and cascaded into off-canvas elements three sections later. The failure surfaced
  as opaque coordinates (`OFF-CANVAS div: box (48,1002)-(1032,1382)`), not as "your body block is
  2x too tall" — I had to reconstruct which logical element that box belonged to from its y-value
  by hand. A measure_text bug produces a valid-looking layout with no local assertion that catches
  "this declared height is implausible for this string," so it can only be caught downstream, by
  the final off-canvas check, several steps removed from the actual mistake.

- **A confusingly wrong "advisory" that I never fully resolved:** `reconcile_boxes` reported
  `BBOX UNDER-REPORTS c1_read: declared 90x22, drawn 447x280` (numbers varied — 554x350, 490x307
  — across iterations, always wildly larger than the declared 90x22). Looking at the actual
  rendered pixels at that location, the "Read →" row is exactly the small size intended — nothing
  is wrong. My best guess is that `read_row()` emits two sibling absolutely-positioned nodes (a
  `<span class="measure">` for the text and an untracked `<svg>` for the arrow icon a few px to
  its right) and reconcile's box-matching attributes some other, much larger drawn box to that
  declared entry — but I could not confirm this by reading `reconcile.py` in the time available.
  This is a case of "a gate stayed noisy on something that was fine" (CLAUDE.md's own stated
  worry — "a check that fires on everything carries no signal") and cost real time convincing
  myself it wasn't a real bug before moving on.

- **`compare.crop()` requires eyeballing fractional coordinates off a rendered view of the source
  image** — there's no assisted phone/device-frame detector, so getting a clean crop of "just the
  middle phone screen" out of a 3-phone mockup took a manual pixel-sampling pass (I wrote a
  throwaway script to sample background colour at 8px intervals down the crop to confirm the
  ground was a single solid orange all the way down, rather than a header band giving way to
  white) before I trusted my own crop box.

- **`RECREATION_PROTOCOL.md`'s central instruction — "apply `shapes.sticker()` to EVERY object,
  uniformly" — does not fit this reference's genre at all**, and the protocol doesn't scope when
  it applies. `shapes.py`/the sticker/die-cut silhouette system is clearly built for badge-pile /
  brand-card references (the worked example in the protocol is exactly that). Applying a die-cut
  halo + ink outline to a plain rounded-rect UI card would have actively broken the fidelity to
  the reference (real app UIs don't have sticker outlines on their cards). I built this with
  plain divs instead and documented why in the script's own docstring, but the protocol reads as
  a universal, non-optional rule ("do exactly what it says, do not improvise") right up until it
  silently doesn't apply — a model with less room to push back could easily sticker-ify a UI
  mockup because the doc told it to, uniformly, no exceptions stated.

Net: score said "badly wrong," eye said "faithful." Followed the documented precedent

alone or my own eye alone without checking both directions.
