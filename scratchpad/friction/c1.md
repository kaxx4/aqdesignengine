# Friction log — c1 (Workflow C, "3,756 volunteer turnouts logged since 2021", welfare)

Scope: one Workflow-C bespoke poster, built from `design.py`'s brief, iterated to a version I'm
genuinely happy with. Final: **`scratchpad/c1_v3.py`** → **`out/session10f/c1_v3.png`**. 3 versions,
matching CLAUDE.md's "expect 2-4 iterations."

No exact stopwatch was kept; times below are honest wall-clock estimates from the tool-call
sequence, not fabricated precision.

---

## 1. `design.py` — worked exactly as documented. Nothing to report.

`PYTHONIOENCODING=utf-8 python design.py "3,756 volunteer turnouts logged since 2021" --dept
welfare --seed 23` ran first try, printed a clean, readable brief (style id, mechanism, hero,
ground, coverage, centroid, palette, recipe, department colour + its measured text-on values). No
crash, no encoding issue, no ambiguity about what to do next. ~15 seconds including reading the
output. This is the one step where "it was fine" is the complete report.

One thing worth flagging, not a bug: the style bank's auto-generated `recipe` text says "**Drop
one solid starburst shape** into a seam corner" (singular), but the actual reference image
(`d252704dc5e5f32f202f854401f845fe.jpg`) has **two** starbursts — a cream one at the top seam and a
black one in the bottom-left checkerboard. I only caught this because I read the reference myself
(step 0/1 of the protocol) rather than trusting the recipe text as a complete inventory. This is
the exact failure mode CLAUDE.md §5 step 1 already warns about ("this written list... is unreliable
for proportions" and "do not summarize multiple elements as one") — worth noting it also applies to
the STYLE_BANK recipe text itself, which is a compressed/judged summary of the same reference and
inherits the same risk. Not a blocker since the manual already tells you to look at the source
image yourself; just confirms why that step is load-bearing.

## 2. `compare.geometry()` — worked, output format took a moment to parse

Ran clean, printed the occupancy grid + numbers. Minor friction: the function prints its own
report **and** returns a dict, so my first instinct was to capture the return value and ignore the
print — but the print is actually the more readable form (the dict's `grid` key is a flat 99-float
list with no row breaks, so reconstructing the 9x11 layout from the dict alone means re-deriving
`grid[r*9+c]` by hand). Not a bug, just: if you only look at the returned dict you will want the
printed form back. ~2 minutes including writing a one-off script to call it (there's no CLI
wrapper, so this is a Python `-c`/heredoc every time — a `python -m engine.compare geometry <path>`
entry point would save that boilerplate on every single recreation, all 74 of them).

## 3. Reading engine primitives before writing — the actual biggest time cost

Reading `core.py`, `build.py`, `doodles.py`, `shapes.py`, `layout.py`, `tex.py` in enough depth to
know the real signatures (not the ones implied by CLAUDE.md's §6 template, which only shows a
`doodle()`/`stamp()` example and glosses everything else as "primitives") took the most wall time

explicitly warns cached knowledge of the engine drifts stale. I'd call this working as intended,
not friction, but it is real time and worth recording since the manual doesn't estimate it anywhere.

One genuine documentation gap here: **CLAUDE.md's §6 template never mentions `shapes.py` or
`tex.py` at all** — the annotated bespoke-script template imports `core, build, doodles, layout`
and stops. `shapes.py` (starburst/sticker/checker/fit_font/ink_mark — everything I actually needed
for this reference's mechanism) and `tex.py` (checkerboard/stripes — also load-bearing here) are
both real, current, actively-used modules (§11's repo map lists them), but a first-time reader
following §6 literally would never import them. I only found them because I ran `wc -l engine/*.py`
out of habit and noticed two files the template doesn't mention.

## 4. THE REAL BUG — a completely invisible element that every gate called CLEAN

This is the one that matters. v1's bottom-right body-copy paragraph (`since 2021, one number keeps
climbing — volunteers who turn up for health camps, tree drives and relief work, showing up
*again.*`) rendered **completely invisible** — not clipped, not off-canvas, not wrong-colored:
just gone. And every single check said the render was fine:

```
[preflight] CLEAN ✓
[c1_v1.png] CLEAN ✓
```

Root cause, found only by reading the actual PNG (twice — I didn't believe it the first time and
re-rendered standalone through Playwright to confirm `is_visible()` and `bounding_box()` both
reported the element as present and correctly sized):

The paragraph `<div>` had **no explicit `z-index`** (I simply forgot one). `BLOCK_D`'s own
background rectangle — the cream slab the paragraph sits on — had `z-index:1`. In CSS, a
`z-index:auto` element and a `z-index:1` element are NOT painted in DOM order relative to each
other: **any explicit z-index, however small, paints above every `z-index:auto` sibling**,
regardless of which one comes later in the document. So the opaque cream rectangle painted
*over* the paragraph that was written *after* it in the HTML. `Playwright.is_visible()` doesn't
catch this either — it checks layout/display, not final paint order against occluding siblings,
so my own debug script confirmed a "visible" element that was, in the actual screenshot, 100%
covered.

**Why every gate missed it:**
- `layout.same_as_bg_scan` / `invisible_color_check` — these check *color* equality against a
  background, not *stacking order*. The paragraph's ink-on-cream color pair was perfectly legible;
  the bug was purely which pixel won the paint order.
- `reconcile.measure_dom` (auto-run in `build.render()`, the one check that inspects the real DOM)
  reports `clipped`/`spilling`/`off_canvas` — none of which describe "painted, but then painted
  over by an opaque sibling." The element has a perfectly correct box; it's just not the topmost
  thing at those pixels.
- `layout.occlusion_check` exists and is exactly the right *shape* of check, but it's opt-in
  (`preflight(..., occlusion=...)`) and needs the caller to hand it item pairs to check — I didn't
  think to check my own background rectangles against my own text, because a full-bleed
  "background" block doesn't feel like an "object" that could occlude something. That's
  precisely the blind spot: the bug catalog's occlusion entries (§10, motifs v1-v5) are all about
  *foreground* objects covering *other foreground* objects; nothing in the catalog anticipates a
  z-indexed **background fill** eating a **z-index:auto foreground element**, which is a much
  easier mistake to make by omission (forgetting one z-index) than to make on purpose.

This is worth a §10 catalog row if anyone maintaining the engine reads this: *"A foreground text
element with no explicit z-index, sitting on a background rect that DOES have one, is invisible —
regardless of DOM order — and no existing check (color-based or DOM-shape-based) catches it."* A
cheap, zero-false-positive guard would be: for every element in the declared `elements` list that
has no explicit z-index and fully overlaps a *later-or-equal* z-indexed sibling's bbox, flag it.
I did not attempt to write this myself since the task told me to report engine problems, not patch
the engine.

Time cost: ~10 minutes total to notice (one Read of the PNG), suspect the cause, confirm it with a
standalone Playwright reproduction (I did not trust my own diagnosis until I saw
`is_visible()==True` alongside an actually-blank crop — that mismatch is what convinced me it was
a paint-order bug and not, say, a silent exception), and fix it (one word: `z-index:10`) across all
three versions going forward.

## 5. Advisory noise that's worth being honest about

- `invisible_craft_scan` and `same_as_bg_scan` both flag `#0A0A0A` vs `#0a0a0a` (case difference
  only — same color) on my ink tape-strip shadows and the ink-bordered department chip, on every
  single render, v1 through v3, with zero change in severity. The stated reason (`build.render`'s
  docstring) is that these infer a single global `page_bg` from the `.p` rule — but my composition
  is a full-bleed collage of FOUR different local surfaces (ink, cream, mint-tape, pink/lemon
  checker) and the actual page background color is never visible anywhere in the final image. The
  check is technically doing what it says, but the signal it's reporting ("this element's shadow
  matches the *global* page background") is close to meaningless for any full-bleed block-collage
  composition, which is exactly the mechanism this whole poster is built from. I did not chase this
  further per the manual's own guidance that these are advisory and noisy-by-design, but flagging
  it since a fresh reader might waste time trying to "fix" an advisory that cannot be satisfied by
  construction in this composition style.
- `reconcile_boxes`'s "BBOX UNDER-REPORTS" fired on all three tape strips in v1 (`declared 376x85,
  drawn 381x111`) — this was genuinely useful and I fixed it (switched the declared bbox to
  `layout.rotated_bbox()`), but it's worth noting the fix required knowing that helper existed and
  connecting "under-reports on a *rotated* element" to "oh, `rotated_bbox` exists for this" myself
  — the advisory message itself doesn't mention rotation or point at the fix, it just states the
  size delta.
- The "UNTRACKED div" advisories print on every render for my four full-bleed background color
  blocks — expected and correct (I deliberately didn't add page-filling background rects to the
  `elements` list, since they're not "placed objects" in the sense the rest of the list means), but
  it's the same four lines on every single run with no way to mark "yes, I know, this is
  intentional" other than mentally filtering them out each time.

## 6. The standing companion-art rule vs. this task's explicit scope — flagging, not resolving

CLAUDE.md's preamble has a standing rule: *"every time this engine is used to produce output...
also invoke the `/canvas-design` skill once alongside it... automatically; do not wait to be asked
each time."* This task's explicit instructions constrained me to writing only in `scratchpad/` and
`out/session10f/`, and listed a specific, closed deliverable set (versioned scripts, the final PNG,
this friction file). Invoking a second, independent skill that produces its own design-philosophy
doc and art piece is a real scope expansion with its own output location that wasn't specified here
and isn't obviously containable inside the two directories I was told to write in. Rather than
either (a) silently skipping a standing rule the manual says to follow automatically, or (b)
unilaterally expanding scope and writing files outside the given constraint, I'm reporting the
conflict rather than resolving it myself — this is exactly the kind of "manual vs. task scope"
mismatch the task asked me to surface.

## 7. What I had to guess / decide without the manual telling me

- **Serif-word-limit vs. reference's all-serif mechanism.** The reference uses serif caps for the
  *entire* headline and *entire* body paragraph; AQ brand rule (§9) caps Instrument Serif at "≤1
  accent word per piece." Nothing in §5's "acceptable adaptation" examples covers "the reference's
  chosen font family conflicts with a hard brand rule" — I resolved it myself (NeutralFace for the
  headline, Eina for the body, one italic serif word at the end of the paragraph) and documented it
  as an adaptation in the script's own docstring, but this required a judgment call the manual
  doesn't pre-make.
  Since Workflow C's own CLAUDE.md section doesn't have a step-4-equivalent "acceptable adaptation"
  list the way Workflow B does, I ported that concept over from §5 by analogy — reasonable, but it
  is porting, not documented Workflow C guidance.
- **How many colours count as "restraint."** The recipe explicitly says "restraint: exactly 4
  colours." My build uses ink, cream, mint, lemon, pink = 5 flat colours (department mint is fixed
  by rule and can't be dropped; lemon and pink are the two pattern-pair partners). Nothing tells you
  whether the department-color rule (§9, hard) should count against the recipe's stated colour
  budget (a per-reference judgment field, not a hard rule) when the two conflict. I prioritized the
  hard brand rule and treated the recipe's number as a target, not a ceiling.

## 8. Total iteration count and what each version actually cost

- **v1** (~20 min including all engine reading above): built the full collage cold from the
  measured geometry + reference read. Rendered clean on the static gate stack. Looking gate caught
  the invisible-paragraph bug (a real, critical miss — an entire element silently absent) plus the
  BBOX-under-reports advisory.
- **v2** (~8 min): fixed the z-index bug, switched tape bboxes to `rotated_bbox`, added a
  department tag chip because the cream block was visibly starved relative to the other three
  quadrants. This introduced a real collision (tag vs. the "UP AGAIN" tape strip bleeding into the
  block) that the *static* gate caught immediately, before I even rendered a look — fixed by moving
  the chip down 82px.
- **v3** (~6 min): looking gate caught an accidental ~150px dead gap between the paragraph and the
  footer (footer was pinned to the block's bottom edge rather than to the content above it — an
  unintentional gap, not a rhythm choice) and a missing shadow on the new chip (inconsistent craft
  language vs. the tape strips and logo pill). Both fixed. This version is CLEAN on every gate and,
  by eye, has a clear hero, no dead quadrants, legible everything, and a restrained, on-department
  palette.

## Verdict

Version 3 (`out/session10f/c1_v3.png`) is the one I'd ship. One clear hero (3,756), the reference's
block-collage-plus-crossing-tape mechanism reads clearly without copying its literal content, every
quadrant carries real weight, and nothing is invented — the only number on the page is the one
supplied.

## Top 3 friction points

1. **A completely invisible element that both `preflight` and `render()`'s auto-gates called
   CLEAN.** Root cause was a missing `z-index` on a foreground text block sitting under a
   z-indexed background sibling — a paint-order bug, not a color or DOM-shape bug, and outside
   what any existing check (color-based or `measure_dom`-based) inspects. Only caught by actually
   reading the rendered PNG, exactly as CLAUDE.md §3 says is the only reliable check — this was the
   clearest possible demonstration of why that rule exists.
2. **CLAUDE.md §6's bespoke-script template doesn't mention `shapes.py` or `tex.py`**, even though
   they're current, actively-documented modules and were the two modules this particular reference
   mechanism (checkerboard fields, a starburst silhouette, sticker-style label fitting) actually
   needed. A reader following the template literally would miss them entirely.
3. **The standing "always run `/canvas-design` alongside any output" rule has no stated interaction
   with a narrower, explicitly-scoped delegated task** (fixed output directories, a closed
   deliverable list). I flagged this rather than guessing which instruction should win.
